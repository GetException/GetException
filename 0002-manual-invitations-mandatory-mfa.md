# ADR-0002: Ручные приглашения и обязательный MFA

Этот ADR заменяет решения ADR-0001 о доставке приглашений через SMTP, подтверждении email перед регистрацией, добровольном TOTP для Developer и Viewer и восстановлении пароля через email. Остальные решения ADR-0001 сохраняются.

## Контекст

GetException устанавливается одной компанией на собственном сервере. Обязательная почтовая доставка усложняет установку и до настройки SMTP полностью блокирует добавление участников. При этом доступ к ошибкам, source maps и настройкам проектов требует сильной аутентификации каждого участника, а не только Owner.

Ручная передача ссылки через корпоративный личный канал убирает зависимость от SMTP, но переносит проверку получателя на Owner и выбранный канал. TOTP защищает последующие входы, однако не исправляет кражу ссылки до регистрации: получивший ссылку первым может настроить собственный пароль и TOTP. Поэтому ссылка остаётся короткоживущим bearer-секретом, а интерфейс явно требует передавать её лично ожидаемому получателю.

## Решение

Owner после password + TOTP step-up создаёт приглашение с нормализованным email, ролью Developer или Viewer и снимком команд. Сервер возвращает случайную 32-байтную ссылку только в ответе создания или перевыпуска. GetException не отправляет её по email. Owner копирует ссылку и передаёт её через доверенный личный канал.

Секрет находится во fragment URL, удаляется из адресной строки сразу после чтения и передаётся серверу только в теле POST. В базе хранится SHA-256 хеш. Ссылка действует 24 часа, используется один раз, отзывается Owner и заменяется новым токеном при перевыпуске. Старый токен после перевыпуска недействителен. Anonymous preview показывает только workspace, пригласившего, роль, команды и маскированный email.

Email остаётся назначенным Owner идентификатором входа. Сервис не утверждает, что пользователь доказал владение соответствующим почтовым ящиком. Свободная регистрация и изменение email из invitation flow запрещены.

Новая учётная запись, membership, team memberships, active TOTP credential, recovery-коды, полноценная auth session и принятие приглашения создаются одной транзакцией только после проверки первого TOTP-кода. После сохранения recovery-кодов пользователь открывает кабинет в этой сессии: повторно вводить тот же уже использованный TOTP-код не требуется. До подтверждения пароль и pending TOTP secret находятся в короткой invitation enrollment session, привязанной к ID и revision приглашения. Незавершённая регистрация не даёт доступа к кабинету.

TOTP обязателен для Owner, Developer и Viewer при каждом входе. Вход разрешает TOTP или один неиспользованный recovery-код. Один временной TOTP-код нельзя применить повторно. Для существующего участника без MFA после обновления пароль открывает только короткий экран обязательной настройки; dashboard остаётся закрыт до подтверждения первого кода.

Критичные действия требуют password + свежий TOTP не старше пяти минут. К ним относятся приглашения, роли и команды, управление MFA, изменение чувствительных настроек проекта, DSN/CI credentials, политика source maps и удаление проекта. Recovery-код разрешён для входа и восстановления фактора, но не заменяет свежий TOTP для обычного административного step-up.

После подключения TOTP выдаётся набор одноразовых recovery-кодов. Они показываются один раз и хранятся только в виде хешей. Изменение пароля или MFA отзывает остальные сессии. Email reset отсутствует. Потерявший TOTP использует recovery-код. Автоматическое восстановление при потере всех факторов в этой итерации отсутствует и требует отдельного решения с подтверждением другого Owner либо offline recovery оператора сервера. Ручное приглашение не сбрасывает MFA существующей учётной записи.

## Безопасность

- ссылка показывается только после свежего Owner step-up и не попадает в query/path, access log, Referer или audit metadata;
- API не возвращает существующий token повторно: для новой копии выполняется ротация;
- rate limit считается по IP и приглашению либо учётной записи;
- pending secret шифруется AES-256-GCM с AAD, содержащим ID enrollment и его состояние;
- принятие сериализуется блокировкой invitation и enrollment и защищено уникальными ограничениями;
- отзыв или ротация invitation инвалидирует enrollment с предыдущей revision;
- audit log хранит тип и результат действия без invitation token, пароля, TOTP secret, кода или recovery-кода;
- старые ожидающие email-приглашения при миграции истекают, а их зашифрованные mail payload очищаются.

## Последствия

Новая установка и добавление участников больше не требуют SMTP. Owner отвечает за передачу ссылки правильному человеку через защищённый личный канал. Компрометация этого канала до завершения регистрации остаётся риском, сравнимым с компрометацией почтового ящика в прежней схеме.

Пользователь не может восстановить доступ через email. Оператор обязан сохранить TOTP encryption key вместе с backup, а пользователи — recovery-коды отдельно от основного устройства. В будущем phishing-resistant passkeys/WebAuthn могут дополнить или заменить TOTP отдельным ADR.
