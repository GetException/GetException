# Account MR !554: интеграция и ёмкость source maps

Исследование от 2026-09-30 по [MR !554](https://gitlab.sndsy.ru/sendsay-ru/frontend/account/-/merge_requests/554), commit `7bc889218f251494bb1d22cb07815095d6440735`.

## Что следует переиспользовать

MR добавляет 5 245 строк в 89 файлах. Около 2 977 новых строк приходится на CI-скрипты и их тесты; 1 662 из них — три файла тестов интеграции с GetException. Основная сложность связана с проверкой подписанного GitLab context, ограничением доступа к картам, восстановлением чистой сборки после частичного `prepare`, безопасной публикацией и обработкой сбоев. Это повторится в следующем приложении.

Sentry разделяет эти задачи: браузерный SDK работает во время исполнения приложения, а [отдельные bundler plugins](https://github.com/getsentry/sentry-javascript-bundler-plugins) готовят source maps, Debug ID и сведения о релизе во время сборки; загрузка выполняется через CLI. Нам подходит тот же раздел ответственности с меньшим набором функций:

1. `@getexception/react`/`browser` оставить для отправки ошибок. CI token, карты и правила deploy не должны попадать в браузерный пакет.
2. Обобщить в `@getexception/cli` получение и строгую проверку контекста CI, диагностику, подготовку нескольких batches, повторную загрузку, регистрацию релиза и проверку публичного output. Это один доверенный Node-инструмент с едиными тестами для всех приложений.
3. Сохранить в Vite-конфигурации приложения только `sourcemap: 'hidden'`, настройку namespace и специфичное для account копирование классических скриптов и CKEditor. Отдельный Vite plugin пока не нужен: подготовка артефактов и upload происходят в Node API CLI после завершения сборки, а общих для нескольких Vite-приложений настроек пока нет.
4. В account оставить привязку `RequestError` к разрешённым API-кодам, маршруты, DSN, команды сборки и deploy. Проверку отсутствия `.map` и credentials в публичном output сохранить обязательной при любом результате мониторинга.

Пакет должен принимать явный контекст проекта и GitLab job, а не зашивать ID репозитория account. Сервер продолжает проверять подпись и область доступа на каждой операции. Нельзя заменять отказ CI identity постоянным токеном или считать неверный ответ разрешением на upload. Переносить весь сценарий deploy/SSH в Vite plugin не нужно.

Реализован экспорт `@getexception/cli/integration`: `deployWithGetException` принимает URL/UUID проекта, release prefix, ID/путь GitLab-репозитория, окружение, путь публичной сборки и callbacks приложения — однократный `beforeBuild` для install/SSH, `build` и `deploy`. Общий код получает и сверяет контекст, удаляет CI-токен из окружения до `beforeBuild`, задаёт безопасное окружение сборки, готовит карты несколькими batches в приватном временном каталоге, проверяет публичный output, регистрирует релиз и загружает карты после успешного deploy. При локальной ошибке подготовки он вызывает `build` ещё раз без карт; callback обязан каждый раз создавать чистый output. Ошибка сборки, deploy или проверки output останавливает job. Сбои мониторинга отражаются в результате и одной безопасной строке лога. CLI-бинарь и его низкоуровневые команды сохраняются для других CI.

## Размер одной сборки

Изолированная production-сборка commit выше с `GETEXCEPTION_SOURCE_MAPS=true`, `GETEXCEPTION_BUILD_NAMESPACE=gl-7-12345` и `sourcesContent` завершилась успешно. Результат до `prepare`:

| Показатель                    |   Значение |
| ----------------------------- | ---------: |
| JS source maps                | 476 файлов |
| Карты на диске, без сжатия    |  60,98 МиБ |
| Передача тех же карт с gzip   |  12,28 МиБ |
| Наибольшая карта              |  10,60 МиБ |
| JavaScript в публичной сборке |  29,41 МиБ |

`prepare` добавляет Debug ID и путь в JSON каждой карты, поэтому итоговый объём будет немного выше. Из-за лимита 128 файлов на upload эта сборка отправляется минимум четырьмя batches. Пределы: 16 МиБ на файл, 128 МиБ на upload, 4 ГиБ на проект, 8 ГиБ на установку и резерв 5 ГиБ свободного места на общем диске. По квоте проекта поместятся примерно **67** таких полных сборок без переиспользования файлов. Gzip сокращает сеть, но хранилище сейчас записывает распакованные карты.

При четырёх полных сборках в неделю поступает около 244 МиБ карт в неделю. За минимальные 30 дней до очистки накопится около 1,02 ГиБ (18 сборок с учётом границ календаря — около 1,07 ГиБ). Если каждая сборка ещё присылает ошибки, удержание продолжается максимум до 60 дней: около 2,04 ГиБ в среднем или 2,14 ГиБ для 36 сборок. Квота проекта 4 ГиБ оставляет примерно 1,9 ГиБ для дополнительных сборок МР при таком сценарии. При большем числе job, росте карт или ещё активной старой сборке квота может закончиться раньше; новые загрузки тогда получат явную ошибку `source_map_quota`, а уже загруженные карты и сохранённые ошибки останутся доступны.

После однократной очистки на сервере свободно 19 ГиБ. Даже если карты достигнут общего предела 8 ГиБ без освобождения старых, останется около 11 ГиБ до роста PostgreSQL, Docker и логов. Дополнительная проверка запрещает новые загрузки карт при остатке менее 5 ГиБ. Она не останавливает рост самой базы: при 1000 событиях в сутки и суммарных 20 КиБ на событие за 30 дней накопится около 0,57 ГиБ, а при 3000 событиях и 50 КиБ — около 4,3 ГиБ. Это сценарии, не измерение будущего трафика; нужно наблюдать реальные размеры базы после запуска и задать отдельный предел/оповещение для неё.

До очистки Docker на production-сервере: диск 30 ГиБ, занято 24 ГиБ, свободно 4,9 ГиБ; приватный volume карт занимает 173 МиБ и содержит 1 464 файла. Основное место занимали 22 ГиБ слоёв Docker/containerd. После удаления 70 старых образов занято 9,7 ГиБ, свободно 19 ГиБ; все контейнеры здоровы. Очистка освободила место на том же диске, но не расширила отдельные квоты карт. Проверка фактического свободного места защищает сервер, если объём Docker снова вырастет.

## Очистка MR-карт

Worker удаляет незавершённые/ошибочные uploads через сутки. Готовый комплект удаляется после 30 дней, когда сохранённые события не используют Debug ID его артефактов, и не позже 60 дней независимо от сохранённых событий. В обоих случаях ожидающие события релиза откладывают удаление до обработки. Кадры без Debug ID консервативно удерживают все карты релиза до предельных 60 дней. У MR каждый GitLab job получает уникальный префикс пути; Debug ID зависит от пути. Поэтому одинаковые исходники соседних jobs почти не экономят место, но событие одного job больше не удерживает карты другого job с тем же `account@SHA`.

**Удалённая карта не стирает уже обработанное событие.** Worker сохраняет `originalFrames` и фрагмент исходного кода в `error_event`; страница ошибки читает их из БД. Новое событие из той же опубликованной сборки после удаления карты получит только compiled stack. У одного issue могут быть оба типа событий, а один release может иметь несколько uploads разных jobs. Поэтому статус карты на release не равен качеству диагностики конкретного события.

Исправленное решение:

1. Не закрывать issue при очистке карты. `resolved` означает, что ошибку исправили, а не что её стало трудно исследовать. События и группы живут по [политике retention](../0003-monitoring-retention.md). В списке issues показывать наличие исходного контекста у выбранного события; фильтр «Has source context» выбирает группы с хотя бы одним расшифрованным сохранённым событием в выбранном release/environment, а «Compiled stacks only» — группы без таких событий. По умолчанию список включает все группы с сохранёнными событиями, включая production-инциденты без карт. В релизах отдельно показывать текущую доступность карт и количество сохранённых событий с исходным контекстом.
2. Помечать release как `Removed`, когда последний готовый комплект его карт удалён. Старый статус `missing` с `sourceMapsVersion > 0` тоже отображать как `Removed`: карта этого релиза прежде была готова. `Not uploaded` оставлять только для `missing` без готовой версии. Если часть job-комплектов одного release останется, агрегированный статус release не докажет наличие карты для каждого Debug ID; для точности при введении ранней очистки надо сохранять историю состояния **каждого** upload/job и показывать «частично доступны».
3. Сохранять у upload подтверждённые сервером назначение `production`/`staging`, точную идентичность job и связь с preview deploy. Существующий `ReleaseDeployment` лишь фиксирует наблюдавшееся окружение, но **не доказывает**, что сборка сейчас развёрнута. Добавить явное подтверждение успешного deploy/stop из доверенного CI или deploy controller. Старую preview-сборку считать выведенной из эксплуатации только после успешной замены в том же MR/environment или подтверждённого stop, затем выдержать окно для открытых вкладок и кэшированных JS (первоначально 7 дней) и дождаться обработки inbox. После этого можно удалить её карты даже при наличии уже расшифрованных событий. Если старый JS всё-таки пришлёт новую ошибку, её отметить как compiled-only.
4. Пока нет достоверного сигнала о действующем deploy, текущая политика удаляет карты после 30 дней без событий с их Debug ID и в любом случае после 60 дней, когда обработаны ожидающие события. Поэтому старая, но ещё развёрнутая сборка может лишиться карты перед следующей ошибкой; это осознанный предел политики без контракта deploy/stop из пункта 3. Заполнение бюджета **не вытесняет** ранее готовые карты. Резерв 5 ГиБ свободного места и предел установки 8 ГиБ проверяются при создании upload и повторно перед записью каждого файла. При исчерпании новые uploads отклоняются. Отдельная квота preview, понятная диагностика в CI/кабинете и уведомление оператора остаются следующими шагами. Сжимать приватные карты на диске как отдельную оптимизацию: измеренная сборка сжимается с 60,98 до 12,28 МиБ, но распаковку и квоты нужно ограничить и протестировать.

Перед внедрением автоматической очистки preview дополнить ADR-0001 и схему БД. Проверить миграцию на пустой и старой базе, замену/остановку deploy, старые вкладки, pending inbox, смешанные jobs одного release, конкурентные uploads и аварийный лимит диска. Текущая 30-дневная очистка карт без событий остаётся рабочей до готовности этого контракта.
