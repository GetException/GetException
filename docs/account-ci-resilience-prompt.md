# Промпт для account: необязательный мониторинг в CI

Продолжи существующую интеграцию GetException в account и MR !554. SDK уже подключён, CLI 0.1.9 установлен, `ci context` v2 реализован. Нужна только доработка поведения CI при сбое мониторинга. Не переписывай logger/SDK и не меняй соседний GetException.

## Требуемый результат

Ни в production, ни в MR недоступность GetException, отсутствие credentials или отказ его API не должны ломать обычную сборку и deploy приложения. Большинство разработчиков не будут включать свои форки в GetException — их рабочий процесс остаётся обычным.

- MR: одна нейтральная строка в логе о картах. Без красного предупреждения, отдельного failed job, призыва обратиться к Owner или включить свой fork.
- Production: заметное предупреждение, если карты не подтверждены или регистрация релиза не удалась. Deploy продолжается.
- Отказ API остаётся отказом. Не превращать 401/403 в успешный policy skip, не ослаблять проверки и не выполнять запрещённый upload.
- SDK с прежними DSN/release/environment продолжает работать независимо от карт. Не добавлять эту логику в React-приложение.

Это согласованное изменение прежнего требования «MR deploy только после ready». Актуальный контракт: соседний `GetException/docs/gitlab-ci.md`, раздел «Обработка сбоев в account», ADR-0001 «Независимость сборки приложения от мониторинга».

## Где менять

Используй существующие `.gitlab/scripts/getexception.ts`, `getexception-output.ts`, `getexception.test.ts`, `deploy-preview.mjs`, `deploy-prod.mjs`, `self-check.mjs` и соответствующие README. Сейчас `initialize/prepare/register` выбрасывают ошибку, которая превращает app deploy в failed. `runCli` выбрасывает stderr и не имеет timeout. Исправь эти места, сохранив реальные проверки и остальные preview sites.

Для независимости deploy от мониторинга достаточно `@getexception/cli@0.1.9`. Для точной диагностики обнови CLI до конкретной версии из подтверждённого выпуска GetException и закрепи её через `yarn add --dev --exact @getexception/cli@<версия>`. Номер версии берётся из сообщения о завершённом выпуске, а не угадывается; не используй `latest`. Browser/react без отдельной причины не обновляй. Сохрани обработку старого CLI общим безопасным кодом.

## Поведение по шагам

1. По умолчанию build environment содержит `GETEXCEPTION_SOURCE_MAPS=false`, пустой monitoring namespace, обычные `account@CI_COMMIT_SHA`, environment и прежний DSN. Credentials удалить из окружения install/compiler/Vite и любых сторонних команд, оставить только в памяти управляющего кода и окружении вызовов CLI. При отсутствии ID token или конфликте legacy token перейти в состояние ошибки мониторинга без карт и без попытки fallback.

2. `initialize` пытается получить `ci context` и строго проверить соответствие SHA/job/environment/MR текущей сборке. Сохранить все проверки v2, точного namespace, source/execution/target и production refs. Валидный `sourceMaps.enabled=true` включает текущий процесс. Валидный `preview_disabled` собирает без карт с доверенным контекстом и возможностью регистрации. Валидный `source_not_allowed` собирает обычный preview без upload/register. Любой иной результат — отдельная ошибка мониторинга: контекст полностью отбросить, продолжить без карт, upload/register не вызывать. Не использовать часть невалидного JSON. Неожиданный skip в production — предупреждение об ошибке интеграции, а не разрешение upload.

3. Разделить локальный prepare, проверку публичного output и сетевой upload. Ошибка prepare может оставить изменённые JS и карты: этот output не публиковать. Управляющий deploy script должен один раз выполнить чистую обычную app build с `sourcemap:false`, без повторного initialize/prepare. Очищать только проверенные рабочие каталоги текущего job существующим безопасным способом. Ошибка обычной компиляции, включая эту единственную пересборку, остаётся ошибкой app job. Не пытаться просто удалить `.map` и развернуть частично изменённый JS.

4. Если prepare и `assertPublicOutput` успешны, сбой upload/ready не требует пересборки. Прекратить загрузку после ограниченных повторов и deploy уже подготовленного проверенного JS. Сохранить точный namespace. Не объявлять доставку полной, пока не готовы все batches. Если Owner отозвал разрешение после initialize, отказ upload обрабатывается так же: доступ не обходится, deploy продолжается.

5. Только после успешного deploy пытаться зарегистрировать возвращённый сервером release/deployment при наличии проверенного контекста, credentials и оставшегося сетевого бюджета. Ошибка регистрации не меняет успех deploy и не откатывает приложение. Если upload уже ready, писать об ошибке регистрации, а не об отсутствии карт. Без проверенного контекста или после `source_not_allowed` регистрации нет. Не сочинять разрешённый контекст на основе локальных CI variables.

6. Ввести явный результат интеграции, различающий: карты готовы, штатно отключены, сбой мониторинга, неполная доставка. Не использовать `deployReady` одновременно для разрешения обычного deploy и успешности upload. Сохранить отдельную обязательную проверку безопасности публичного output во всех ветвях. Логировать итог один раз, а не для каждого batch. Для MR достаточно `[getexception] Preview without source maps.` либо `[getexception] Source maps unavailable; preview continues.`; при готовых картах и сбое регистрации — отдельная точная нейтральная формулировка. Для production — заметный `WARNING` с фактическим результатом мониторинга, без остановки.

7. Жёсткие ограничения ожидания: context/register до 10 секунд каждый; общий бюджет всех сетевых вызовов GetException до 60 секунд на job, суммарно по batches/повторам/регистрации. Время install/build/deploy этот бюджет не расходует. Каждый upload получает оставшееся время, после исчерпания новые запросы не выполняются. У локального prepare также конечный timeout; его timeout ведёт к одной чистой пересборке. Завершать зависший CLI и его дочерние процессы, не оставлять фоновую загрузку с token. Не прятать timeout под успешный upload.

8. Очистка выполняется во всех исходах и только для собственных приватных каталогов текущего job, с прежними проверками realpath/inode/symlink. Ошибка cleanup после уже успешного deploy не должна превращать его в failed или приводить к опасному расширению удаляемого пути. Вывести безопасный фиксированный код, не включать приватные каталоги в artifacts/cache. Если безопасность публичного output подтвердить нельзя, его публикация запрещена.

## Безопасная диагностика

Нельзя печатать сырой stdout/stderr неуспешного CLI, `error.message`, stack/cause, JWT, headers, response body или значения claims. Сохрани ограничение размера захваченного output. Ошибки запуска и timeout определять по exit/signal и фиксированным кодам.

CLI с поддержкой диагностики при ошибке возвращает exit 1 и одну строку:

```text
GETEXCEPTION_DIAGNOSTIC {"version":1,"code":"CI_IDENTITY_CONFIG","httpStatus":401,"requestId":"11111111-1111-4111-8111-111111111111"}
```

Поддержи её безопасный разбор уже сейчас: принять только известную версию, точные ключи, code из фиксированного enum, необязательный HTTP status 100–599 и UUID requestId; затем заново сформировать строку из этих полей. Код не должен быть произвольной строкой даже при ограничении длины. Полный allowlist смотри в соседних `packages/protocol/src/ci-diagnostics.ts` и `packages/cli/src/diagnostics.ts`; значения протокола скопировать в именованный локальный контракт и проверить тестами допустимых и недопустимых сообщений. Ни runtime, ни тесты account не должны зависеть от наличия соседнего checkout GetException. Неподдерживаемый/старый формат, несколько неоднозначных диагностических строк или посторонние поля дают фиксированный `COMMAND_FAILED`, без вывода оригинала. Для MR можно добавить code/status/requestId к одной нейтральной строке; для production — к предупреждению. Реальную причину pipeline 9779/job 91540 по старому общему сообщению не выдумывать.

## Безопасность, которую сохранить

- `assertPublicOutput` выполняется перед каждым deploy, в том числе после fallback и при выключенных картах. Ошибки этой проверки не являются необязательными ошибками мониторинга.
- `.map`, `.map.gz`, `.map.br`, inline maps, приватные manifests/каталоги и credentials не попадают в публичный output, GitLab artifacts/dotenv reports/cache или Turbo cache. Сохранить различие настоящего sourceMappingURL-комментария и безвредной строки-шаблона библиотеки.
- Никаких постоянных token fallback, снятия Protected, production secrets в MR, wildcard-разрешений, изменения origins, подмены SHA/namespace или карты от последней другой сборки.
- Не ставить `allow_failure: true` всему app job, не добавлять `|| true` всему deploy и не поглощать ошибки install/обычной сборки/SSH/rsync. Мониторинг обрабатывает только свои ошибки.
- Не менять серверные настройки или allowlist из account. Деплой обычного MR не требует действия Owner.

## Проверки

Добавь тесты поведения управляющего deploy flow, а не только вспомогательных функций:

- MR и production продолжают build/deploy при недоступности сервера, отсутствии token, 401/403/429/5xx, timeout, невалидном JSON, неизвестном контракте и контексте другого SHA/job. Нет upload/register с непроверенным контекстом.
- Обе штатные ветви skip сохраняют прежнюю семантику; продакшен на skip продолжает deploy с предупреждением.
- Enabled + все batches ready: прежние prepare/upload/registration работают. Сбой на одном batch, timeout ready или отзыв разрешения после initialize: deploy проверенного JS продолжается, успех всех карт не заявляется.
- Частично изменённый output при prepare failure не публикуется; выполняется ровно одна чистая сборка без карт. Её реальная ошибка блокирует deploy.
- Ошибка регистрации после deploy сохраняет успешный app job. MR получает одну нейтральную строку, production заметный WARNING. При готовых картах и ошибке регистрации сообщение точное.
- Зависший CLI ограничен timeout; десятки batches делят общий сетевой бюджет, а не каждый ждут его заново. После исчерпания вызовов нет, token не остаётся в дочернем процессе.
- Во всех ветвях утечка карт/credentials в публичный output блокирует публикацию. Обычная ошибка build или rsync по-прежнему ломает app job.
- Canary в exception/body/JWT/headers/CLI stderr не появляется в логе; допустимы только фиксированные code/status/UUID. Старый CLI с общим stderr не блокирует deploy.
- Сохранены реальные Vite tests для entry/dynamic chunks/namespace, приватные файлы не сохраняются в artifacts/cache.

Обнови self-check и README под новый контракт, запусти проверки account. Не выдавай моки за проверенный MR pipeline. В результате коротко укажи, что изменилось, какие проверки прошли и что требует нового запуска реального app job. Публикация новой диагностики GetException не должна быть обязательной для этого исправления.
