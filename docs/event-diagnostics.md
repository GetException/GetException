# Диагностика ошибок и source maps

## Дополнительные поля

Новая версия SDK принимает контекст конкретного события:

```ts
GetException.captureException(error, {
  contexts: {
    api: { code: "error.request", reason: "rate_limited", status_code: 429 },
  },
});
```

Также поддерживается `scope.setContext("api", ...)` внутри `withScope`; контекст и теги этого scope не переходят в следующее событие. Старый `captureException(error)` сохраняет совместимость. Исходные Error/RequestError и их stack сохраняются; SDK не извлекает произвольные поля, request/response или текст причины из объекта ошибки.

`code`: до 64 ASCII-символов, первая буква, затем буквы, цифры, `_`, `.` или `-`; также допускаются числовые коды из 1–6 цифр. Передавайте только документированные технические коды API. `reason`: `network_error`, `timeout`, `aborted`, `unauthorized`, `forbidden`, `not_found`, `validation_error`, `conflict`, `rate_limited`, `server_error`. Неизвестные причины пропускайте; нельзя подставлять произвольный текст ответа. `status_code`: целое 100–599. Неверные и лишние поля независимо отбрасывают SDK и ingest.

Браузер определяется автоматически: Chrome, Edge, Firefox, Safari, Opera, Samsung Internet и только major-версия. Полный User-Agent не включается в payload и не хранится в БД; неизвестные браузеры не получают выдуманного семейства. Эти данные и API-контекст отображаются в Event details. Это сведения клиента, а не доверенные признаки для авторизации.

## Source maps в account

Актуальная схема для MR — [прямая загрузка с удостоверением GitLab](gitlab-ci.md). Она не выдаёт постоянный CI token коду MR и не сохраняет карты в GitLab artifacts/cache. Описанные ниже постоянные upload tokens применимы только к доверенному CI.

После выпуска новой версии сервера и npm-пакетов:

1. Обновить `@getexception/react` и добавить dev dependency `@getexception/cli` из одного нового релиза. Убедиться, что SDK использует `release: account@<полный CI_COMMIT_SHA>`.
2. Включить hidden/external JS source maps с `sourcesContent` в сборке account.
3. Owner создаёт отдельный токен в Projects → account → Settings → Source map upload tokens. Сохранить его в GitLab как секрет `GETEXCEPTION_UPLOAD_TOKEN`; ID проекта — переменная `GETEXCEPTION_PROJECT_ID`. Токен никогда не попадает в `APP_*`, `VITE_*` или browser bundle. Доступ к нему только у доверенных CI jobs; не раскрывать секрет коду чужих MR.
4. После сборки, до упаковки/deploy выполнить `prepare`, затем `upload` по [инструкции CLI](../packages/cli/README.md). Публиковать именно подготовленный JS. Для MR дождаться загрузки до deploy; при непроверенных правах GitLab не сохранять карты в artifacts/cache даже при сбое. Постоянный token нельзя выдавать MR для обхода отказа OIDC.
5. В `sentryLogger` добавить только разрешённые API-поля из явного преобразования RequestError. Browser не нужно заполнять вручную. Уже добавленные routes, tags и breadcrumbs оставить.

Карты выбираются в пределах проекта и релиза по Debug ID; для старого SDK без ID допускается точное совпадение URL path, только если кандидат один. Две разные сборки того же SHA с тем же именем JS требуют Debug ID. Неизвестный Debug ID не подменяется совпадением по пути.

## Закрытый upload API

Все запросы идут на HTTPS dashboard origin с `Authorization: Bearer <upload token>` и без Origin/cookies. Session и публичный DSN не дают права загрузки.

- `POST /api/v1/projects/:project/source-maps`: JSON `{release, artifacts:[{path, debugId, sha256, size}]}`; ответ `{uploadId,status,artifacts:[{id,path}]}`.
- `PUT /api/v1/projects/:project/source-maps/:upload/:artifact`: содержимое одного JSON map, `Content-Type: application/json`.
- `POST /api/v1/projects/:project/source-maps/:upload`: подтвердить комплектность, поставить проверку в очередь.
- `GET /api/v1/projects/:project/source-maps/:upload`: только статус `receiving/pending/validating/ready/failed` и фиксированный код ошибки, без содержимого карты.

Публикация атомарна для всего upload: worker проверяет checksum, v3-структуру, Debug ID, имя JS и mappings всех файлов. Parser выполняется в отдельном worker thread без переменных окружения родителя, с лимитом памяти и пятисекундным deadline. Один parser на процесс, последовательная очередь чтения файлов; production worker подключён только к внутренней сети БД и не скачивает исходники по URL. Несколько worker-процессов используют leases с heartbeat и защитой от устаревшего владельца.

Поздняя загрузка увеличивает версию карт релиза. Worker повторно обрабатывает его события, пересчитывает группировку, сохраняет историю переноса. Уже решённая ошибка не становится regression из-за одной лишь загрузки карт. Исходный stack остаётся рядом с восстановленным; UI выводит исходный код как текст.

## Хранение и восстановление

Миграции повышают схему БД до 6, существующие события сохраняются. Откат на релиз со схемой 4 или 5 требует соответствующей резервной копии БД; автоматический откат несовместимых образов запрещён.

В Docker карты хранятся в постоянном приватном volume `getexception_source-maps`: web пишет, worker-events читает, worker-retention удаляет. Ingest, Caddy и mail не имеют mount. При native `local:start` каталог — `runtime/local/source-maps`. У самостоятельных dev-процессов одинаковый `SOURCE_MAP_DIR` или общий `.local/source-maps` из корня репозитория.

Текущий `getexception backup` сохраняет PostgreSQL, **не содержимое source-map volume**. Для полного восстановления дополнительно резервируйте этот volume с ограниченным доступом либо сохраняйте приватные артефакты CI. Повторная загрузка того же manifest восстанавливает недостающие файлы после восстановления БД. Обычное обновление контейнеров volume сохраняет.

Незавершённые/отклонённые загрузки очищаются через сутки; готовые карты — после 30 дней, когда не осталось сохранённых событий релиза. Удаление проекта сохраняет семь дней восстановления, затем метаданные удаляются порциями и retention удаляет осиротевшие файлы.

## Проверка вручную

1. Создать CI-токен под Owner, подготовить и загрузить карты тестовой сборки. В Releases увидеть `ready`.
2. Внутри исходного файла приложения выполнить ошибку из обработчика действия (ошибка из DevTools будет `<anonymous>`). Открыть событие: проверить исходный `.ts/.tsx`, функцию, строку, фрагмент кода и отдельно compiled location.
3. Отправить обработанный RequestError с разрешёнными API-полями. Проверить API code/reason/HTTP status, браузер с major-версией, breadcrumbs и route. Следующее событие не должно наследовать контекст предыдущего.
4. Отправить ошибку до загрузки карт другого релиза. После upload дождаться восстановления кадра и увидеть Grouping history, если группа поменялась.
5. Отозвать токен и повторить upload: отказ 401. DSN и обычная сессия тоже не разрешают upload. Ошибки продолжают приниматься по DSN.

## Релизы, окружения и MR

Релиз остаётся `account@<полный SHA>`. Новый коммит в MR создаёт другую версию после первого события или регистрации из CI. Один SHA в production и preview — один релиз с двумя метками. В Releases доступны фильтры Production, Preview / staging и Development. Preview-сборки с известным MR сгруппированы в пределах текущей страницы; ссылка MR открывает все его сборки с пагинацией. Счётчики и переходы со страницы релиза учитывают выбранное окружение.

Миграция сохраняет окружения существующих событий; новые фиксирует worker. Эти метки остаются после удаления событий по retention. Номер MR из SHA, домена или `staging` не угадывается. CI регистрирует его отдельно командой `releases register` из [инструкции CLI](../packages/cli/README.md), даже если карты для preview не загружаются. `POST /api/v1/projects/:project/releases` принимает `{release, deployment: {environment, review?: {provider: "gitlab", repositoryId, number}}}`. Только project-scoped upload token, HTTPS, без Origin; MR разрешён только для staging. Пользовательские URL, имена веток и тексты MR не сохраняются. Регистрация повторяема и не доказывает, что версия всё ещё активна на сервере.

Debug ID вычисляется из JS, карты и пути. Одинаковые артефакты разных релизов одного проекта используют один приватный файл; upload передаёт лишь недостающие файлы, но каждый релиз регистрирует свой manifest. Изменение JS или карты меняет ID. Одинаковый ID с другим содержимым отклоняется. Карта «последнего релиза» не используется. Для нового JS карту нужно сгенерировать заново; для неизменившихся файлов экономятся передача и место.

Retention убирает ссылки старых комплектов без сохранённых событий и ожидающих событий inbox. Физический файл удаляется только после исчезновения всех ссылок. Лимиты объёма учитывают уникальные файлы; предел 100000 записей артефактов ограничивает также рост метаданных. Если карты для MR не загружаются, события продолжают приниматься, но стек остаётся скомпилированным.

Проверка интерфейса: зарегистрировать две версии staging с одним MR, открыть Preview / staging → MR и сравнить сборки. Зарегистрировать одну из версий в production, проверить обе метки и раздельные счётчики. У версии без номера MR не должна появляться выдуманная метка MR. Старые события без карт показывают Not uploaded.
