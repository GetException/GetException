# Инструкции для работы с GetException

## Назначение проекта

GetException является monorepo для личного кабинета, сервера приёма ошибок, фоновых worker и npm-пакетов `@getexception`. Лендинг хранится в отдельном репозитории `getexception.github.io`.

Перед изменением архитектуры прочитайте [ADR-0001](./0001-sentry-compatible-error-monitoring-platform.md), [словарь контекста](./CONTEXT.md), [аудит безопасности](./SECURITY-AUDIT.md) и [разбор референсных проектов](./REFERENCE-PROJECTS.md). Если реализация требует изменить принятое решение, сначала обновите ADR или добавьте новый ADR.

## Пакетный менеджер

- Используйте только Yarn, указанный в поле `packageManager` корневого `package.json`.
- Yarn должен работать через обычный каталог `node_modules`. Plug and Play использовать нельзя.
- Добавляйте и обновляйте зависимости командами Yarn. Не редактируйте `yarn.lock` вручную.
- Все npm package names должны использовать scope `@getexception`. Публикуемые пакеты должны иметь явный `publishConfig.access: public`, а внутренние пакеты должны иметь `private: true`.

## Обязательные проверки

Перед каждым коммитом запустите из корня:

```bash
yarn checks
```

Коммит можно создавать только после успешного завершения команды. Корневой script `checks` должен запускать все обязательные проверки проекта. При добавлении typecheck, тестов, сборки или других проверок добавьте их в этот script.

Используйте Prettier для форматирования и ESLint для проверки JavaScript и TypeScript. Не отключайте правила для всего проекта ради одной ошибки. Локальное отключение правила должно содержать короткое объяснение.

## Архитектурные границы

- `apps/ingest` принимает недоверенные события, проверяет и очищает их, записывает в PostgreSQL inbox и быстро отвечает клиенту.
- `apps/worker` выполняет symbolication, группировку, пересчёт статистики и retention. Тяжёлая обработка не должна выполняться в запросе ingest или web.
- `apps/web` обслуживает личный кабинет, авторизацию и закрытое API.
- `packages/browser` и `packages/react` сохраняют заявленную совместимость с поддерживаемой частью API Sentry.
- Серверные проверки доступа, очистка payload и разделение PostgreSQL-ролей нельзя заменять клиентскими проверками.

## Секреты и данные

- Не добавляйте `.env`, `NPM_TOKEN`, пароли, DSN upload tokens или другие секреты в Git, логи, fixtures и build artifacts.
- В `.env.example` разрешены только пустые значения и безопасные примеры.
- `NPM_TOKEN` хранится локально в `.env`, а в CI в GitHub Secret с тем же именем. Токен доступен только job публикации.
- Не сохраняйте исходный payload ошибки. Используйте только разрешённые и очищенные поля из ADR.

## Изменения и тесты

- Сохраняйте обратную совместимость поддерживаемого API `@sentry/browser` и `@sentry/react` или явно документируйте отличие.
- Добавляйте тест на исправленную ошибку и на новую ветвь поведения.
- Проверяйте миграции на пустой базе и на базе предыдущей версии.
- Не смешивайте в одном коммите несвязанные изменения.
- Не изменяйте и не удаляйте пользовательские изменения, которые не относятся к текущей задаче.
