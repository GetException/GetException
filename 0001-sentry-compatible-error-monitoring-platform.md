# ADR-0001: Создать GetException как Sentry-совместимый сервис мониторинга ошибок

## Статус

Решение принято для реализации MVP.

Название продукта и основного репозитория — **GetException**. Публичные npm-пакеты используют scope **@getexception**.

Термины, которые используются в документе, зафиксированы в [словаре контекста](./CONTEXT.md). Подробная проверка угроз и обязательных защит находится в [аудите безопасности](./SECURITY-AUDIT.md); требования с пометкой «блокирует production» являются частью этого ADR, а не необязательными рекомендациями.

Этот ADR является отправной точкой для создания MVP. Если код или более поздний ADR не уточняет решение, реализация должна следовать требованиям этого документа.

## Краткое решение

Мы создаём отдельный self-hosted-сервис для одной компании. Он принимает ошибки из обычных browser SPA и React SPA, включая **app**, **transport**, **x-editor** и другие редакторы, безопасно очищает их от лишних данных, объединяет одинаковые ошибки, показывает их в закрытом личном кабинете и связывает с релизами и source maps.

Первая версия занимается только ошибками. Трейсинг производительности, запись действий пользователя, логи как отдельный продукт, мобильные SDK и прочие функции Sentry в MVP не входят.

MVP состоит из двух пользовательских частей:

1. личный кабинет;
2. npm-пакеты для обычного browser SPA и React SPA.

Лендинг находится в отдельном репозитории GitHub с именем `getexception.github.io`. Он публикуется через GitHub Pages по адресу `https://getexception.github.io` и не входит в monorepo или серверный deploy MVP.

Внутри сервера будут три типа runtime-процессов:

- **web** — Next.js: личный кабинет, вход, настройки и закрытое API;
- **ingest** — небольшой публичный приёмник ошибок на Node.js/TypeScript;
- **worker** — отдельные режимы обработки ошибок, служебных писем и retention.

Все процессы поставляются Docker-контейнерами. Основная база — PostgreSQL. В первой версии Redis не нужен.

## Почему создаём отдельный продукт

Новый сервис не является частью существующих **app**, **transport** или **x-editor**. Он разворачивается отдельно и подключается к любому из них через npm-пакет. Это позволяет:

- независимо обновлять мониторинг и наблюдаемые приложения;
- использовать один сервис для нескольких проектов;
- позже подключать другие browser SPA и React SPA;
- ограничить права публичного приёмника и не смешивать его с бизнес-API приложений;
- при необходимости заменить сервис, не переписывая все вызовы Sentry.

## Исходные условия

- одна установленная копия сервиса предназначена для одной компании;
- наблюдаемые browser SPA и React SPA: app, transport, x-editor и дополнительные редакторы;
- суммарно ориентируемся примерно на 2 000 конечных пользователей в день;
- ожидаемый объём ошибок небольшой, но нужен запас на всплески;
- вход в личный кабинет — по email и паролю, без входа через Google;
- в личном кабинете только заранее зарегистрированные участники;
- регистрация происходит только после приглашения администратора;
- участник должен видеть только проекты назначенных ему команд, кроме Owner с глобальным доступом;
- три предустановленные роли;
- интерфейс строится на Next.js и [Base UI](https://base-ui.com/);
- база данных — PostgreSQL;
- личный кабинет, ingest, worker и публичные npm-пакеты разрабатываются в одной monorepo `GetException`;
- GetException разворачивается на отдельном Linux-сервере и не зависит от GitHub Pages;
- локальный запуск, bootstrap, CI/CD, аутентификация и деплой используют конкретные решения из Selflify, Selfchecks и AppNotes, перечисленные в разделе о референсных проектах;
- публичные Docker-образы и npm-пакеты проходят отдельные build, publish и smoke test jobs;
- лендинг разрабатывается и выпускается независимо от рабочего MVP.

## Что входит в MVP

- автоматический перехват необработанных JavaScript-ошибок;
- автоматический перехват необработанных rejected Promise;
- React ErrorBoundary;
- ручная отправка исключения;
- ручная отправка сообщения только уровней **error** и **fatal**;

- проверка формата, ограничение размера и очистка каждого события;
- защита от очевидного спама и перегрузки.

- простая статистика без системы пользовательских отчётов.

### Управление

- вход по email и паролю;
- приглашение и управление зарегистрированными участниками;
- команды и назначение проектов командам;
- обязательная двухфакторная защита Owner;

- выпуск и замена публичного DSN;

- управление сроком хранения событий и лимитами проекта.
- одноразовая первоначальная настройка домена установки и root-пользователя при первом открытии кабинета;
- настройка TOTP через Google Authenticator, 1Password или другое совместимое приложение.

### Эксплуатация

- Docker Compose для локальной и production-среды;
- миграции PostgreSQL;
- однострочный bootstrap новой установки;
- CI-проверки;
- сборка и публикация Docker-образов;
- публикация npm-пакетов;
- проверка уже опубликованных пакетов на тестовых browser SPA и React SPA;
- health checks, резервное копирование, восстановление и откат.

## Что не входит в MVP

- performance tracing и транзакции;
- session replay и запись экрана;
- profiling;
- логи как отдельный раздел;
- пользовательские отзывы;
- вложения;
- browser sessions и release health;
- метрики и check-ins;
- email, Telegram, Slack и другие уведомления;
- Node.js/backend и Next.js server SDK;
- Vue, Angular, мобильные и нативные SDK;
- открытая регистрация любой компании;
- несколько независимых компаний в одной установленной копии;
- полная совместимость с административным API Sentry;
- полная совместимость со всеми командами sentry-cli;
- импорт исторических данных из Sentry.

## Главная граница безопасности

Браузер конечного пользователя находится **за границей доверия**. Мы не доверяем:

- самому браузеру;
- установленным расширениям;
- данным конечного пользователя;
- JavaScript-коду, изменённому через DevTools;
- любому событию, пришедшему на публичный адрес;
- заголовкам Origin и Referer как доказательству личности;
- открытому DSN.

В browser SPA невозможно надёжно спрятать постоянный секрет. Всё, что попало в JavaScript bundle, публичную переменную окружения, HTML или сетевой запрос, пользователь может прочитать. Поэтому схема «положить Deploy key в приложение и отправлять hash(JSON + key)» не подтверждает подлинность события: злоумышленник достанет этот же ключ и подпишет любой JSON. JWT, подписанный постоянным секретом внутри SPA, имеет ту же проблему.

Граница доверия начинается только:

- на нашем сервере после проверки и очистки входного события;
- в закрытом личном кабинете после входа и серверной проверки роли;
- в доверенном CI, где хранится секрет загрузки source maps;
- на production-сервере и в его закрытой сети.

Личный кабинет и публичный приёмник используют разные origins, например `monitor.example.com` и `ingest.monitor.example.com`. Session cookie создаётся только на host личного кабинета; ingest не получает и не использует пользовательские cookie.

```text
Недоверенная зона

Browser SPA конечного пользователя
        |
        | HTTPS + событие + публичный DSN
        v
+-----------------------------------+
| Публичный приёмник ingest         |
| Проверяет, ограничивает, очищает   |
+----------------+------------------+
                 |
=================|================================  граница доверия
                 v
+-----------------------------------+
| PostgreSQL inbox                  |
| Только очищенные события          |
+----------------+------------------+
                 v
+-----------------------------------+
| Worker                            |
| Source maps, группировка, счётчики|
+----------------+------------------+
                 v
+-----------------------------------+
| PostgreSQL: события и группы      |
+----------------+------------------+
                 |
                 | Только после входа
                 | и проверки роли на сервере
                 v
+-----------------------------------+
| Next.js личный кабинет            |
+-----------------------------------+

Доверенный CI проекта
        |
        | HTTPS + секретный upload token
        v
Закрытое хранилище source maps
```

## Как приложение отправляет ошибки

### Решено: публичный DSN, как у Sentry

После создания проекта личный кабинет формирует DSN следующего вида:

```text
https://<public-key>@errors.example.com/<project-id>
```

Это не пароль. Он попадёт в браузер и будет виден конечному пользователю. DSN даёт только одно право: **попытаться прислать событие в один проект**.

Он не позволяет:

- читать ошибки;
- видеть статистику;
- входить в личный кабинет;
- менять проект;
- приглашать участников;
- отмечать ошибку решённой;
- загружать или скачивать source maps;
- работать с другим проектом.

Сервер хранит не сам публичный ключ, а его односторонний хеш. Ключ можно заменить; старый ключ некоторое время работает параллельно, чтобы приложения успели обновиться, после чего отзывается.

### Свойства безопасности публичного DSN

Если DSN узнает посторонний человек, он сможет прислать фальшивые ошибки в пределах установленных лимитов. Это зафиксированный остаточный риск. DSN не открывает сохранённые данные и не даёт административных прав: его утечка создаёт риск шума или расхода ресурсов, но не раскрывает пользовательские данные из сервиса.

Риск фальшивых событий уменьшают:

- точный список разрешённых origin;
- лимит запросов на IP;
- отдельный лимит на проект;
- дневная квота;
- максимальный размер тела запроса;
- ограничение числа элементов и глубины JSON;
- подавление точных повторов;
- возможность немедленно отозвать ключ;
- отдельный контейнер и отдельный пользователь БД для публичного приёмника;
- внешний сетевой rate limit в Caddy;
- возможность позже поставить CDN/WAF перед endpoint.

Origin — полезный фильтр для обычного браузера, но не средство входа. Скрипт вне браузера может написать любой заголовок. Поэтому в интерфейсе нельзя обещать, что разрешённый домен доказывает источник события.

Если в будущем понадобится криптографически подтверждать отправителя, наблюдаемое приложение должно получать короткоживущий токен от своего backend. Для универсального SPA-пакета это не является обязательным MVP-режимом.

## Публичный приёмник ошибок

Приёмник реализует совместимый endpoint:

```text
POST /api/<project-id>/envelope/
```

Envelope — это текстовый контейнер Sentry: сначала служебная строка, затем описание типа данных и JSON самого события. Приёмник понимает контейнер, но сохраняет только один элемент типа **event**.

До записи в базу приёмник обязан:

1. принимать запрос только по HTTPS через reverse proxy;
2. разрешать только метод POST;
3. найти проект по project ID и хешу публичного ключа;
4. отклонить неизвестный, выключенный, просроченный или отозванный ключ;
5. проверить Origin, если браузер его прислал;
6. применить лимиты IP, проекта и всей установки;
7. проверить размер сжатого и распакованного тела;
8. принять не более одного события ошибки;
9. проверить framing Envelope и JSON;
10. проверить число полей, длину строк, глубину объектов и размеры массивов;
11. рекурсивно отклонить специальные ключи `__proto__`, `prototype` и `constructor`;
12. создать **новый безопасный объект** только из разрешённых полей, без deep merge или spread недоверенного объекта;
13. дополнительно удалить похожие на токены, пароли и персональные данные фрагменты;
14. назначить серверный `received_at`, ограничить присланное время разумным окном и проверить форматы event/release/environment/Debug ID;
15. записать только новый очищенный объект параметризованным запросом;
16. никогда не писать исходное тело запроса в логи;
17. вернуть короткий общий ответ без echo события, SQL/stack trace и лишних сведений о проекте.

Первичные лимиты:

- один event на Envelope;
- событие до 1 MiB;
- Envelope до 1,25 MiB после распаковки;
- не более 100 stack frames;
- не более 50 безопасных breadcrumbs;
- не более 50 tags;
- ключ и значение tag имеют жёсткий лимит длины;
- неизвестные поля отбрасываются;
- запрещённые типы Envelope не сохраняются;
- неизвестные `Content-Type` и `Content-Encoding`, вложенное сжатие и несколько authentication payload отклоняются;
- при временном лимите возвращается HTTP 429 и совместимые с выбранной версией SDK заголовки.

Начальная политика потока:

- один проект: в среднем до 20 событий/секунду, краткий всплеск до 50;
- один IP: в среднем до 10 событий/секунду, краткий всплеск до 30;
- вся установка: до 100 000 принятых событий/сутки;
- один проект: 25 000 событий/сутки по умолчанию; Owner может изменить значение в пределах общего лимита.

При превышении ingest возвращает HTTP 429 и не сохраняет событие. MVP не выполняет незаметную выборочную запись событий. Число отказов считается по проекту и причине и показывается в кабинете. Значения являются конфигурацией и подтверждаются нагрузочным тестом до production.

## Какие данные разрешено сохранять

### Разрешено по умолчанию

- случайный event ID;
- время события;
- название и версия нашего SDK;
- платформа JavaScript;
- уровень только error или fatal;
- проект, окружение, релиз и dist;
- тип исключения;
- очищенное и укороченное сообщение;
- признак handled/unhandled;
- stack frames: имя файла, имя функции, строка, колонка, in-app, Debug ID;
- маршрут страницы без протокола, домена, query и hash;
- семейство и основная версия браузера;
- безопасные tags: feature, component, operation и разрешённые Owner имена;
- до 50 элементов безопасной технической истории перед ошибкой;
- необязательный анонимный идентификатор конечного пользователя.

### Всегда отбрасывается в MVP

- cookie;
- Authorization и другие HTTP-заголовки;
- тела запросов и ответов;
- query-параметры и URL fragment;
- IP-адрес и геолокация;
- email, имя, телефон и username конечного пользователя;
- localStorage, sessionStorage и IndexedDB;
- Redux/store state;
- React props и state;
- содержимое DOM и введённые в формы значения;
- загруженные файлы;
- локальные переменные stack frame;
- pre-context, context-line и post-context, присланные браузером;
- произвольные extra и неизвестные contexts;
- объекты из console;
- DOM-селекторы и видимый текст элементов;
- replay, tracing, profile, attachment, feedback, session, metric и check-in.

### Идентификатор конечного пользователя

SDK ничего не узнаёт о пользователе автоматически. Наблюдаемое приложение может явно передать случайный технический идентификатор, созданный специально для мониторинга. Нельзя передавать email, логин, телефон, access token или внутренний секрет.

Смысл идентификатора — посчитать, затронула ошибка одного человека сто раз или сто разных людей. Из личного кабинета GetException невозможно будет узнать, кто этот человек, без отдельного сопоставления в исходном приложении.

### Решено: безопасная история перед ошибкой

Перед событием сохраняется не более 50 последних технических действий:

- переход на маршрут без протокола, домена, query-параметров и fragment;
- запрос к API: HTTP-метод, очищенный путь или шаблон маршрута, статус и длительность;
- вручную добавленное приложением действие с разрешённой категорией и примитивными значениями.

Не сохраняются клики по DOM, текст кнопок и страниц, значения форм, тела запросов и ответов, заголовки, cookie, console arguments и произвольные объекты. Безопасная история предназначена только для понимания технической последовательности перед ошибкой и не является session replay.

### Решено: tags

По умолчанию разрешены короткие метки **feature**, **component** и **operation**. Owner может добавить для проекта другие разрешённые имена. Имя и значение проходят ограничения длины и очистку; вложенные объекты запрещены. Project, release и environment являются отдельными полями и не дублируются в tags.

### Двойная защита

Фильтрация в npm-пакете нужна, чтобы лишнее по возможности не покидало браузер. Но это не граница безопасности: пользователь может изменить пакет или сам отправить запрос. Поэтому сервер независимо повторяет проверку и собирает безопасное событие с нуля.

Сохранённое событие остаётся недоверенным и после очистки. Строка, похожая на SQL, HTML или JavaScript, не выполняется: SQL всегда параметризован, а кабинет выводит поля только как текст. Поля события никогда не используются как shell-команда, непроверенный путь, URL для серверного запроса, регулярное выражение или имя части SQL.

IP может кратковременно обрабатываться Caddy/ingest только для rate limit. Он не добавляется к событию, не попадает в audit log и постоянную статистику и удаляется вместе с коротким техническим окном limiter.

Автотесты кладут тестовый «секрет» в URL, cookie, хранилище, форму, React state, объект ошибки и API-ответ. После искусственной ошибки тест подтверждает, что эта строка отсутствует:

- в отправленном сетевом запросе;
- в логах ingest;
- в очереди;
- в таблице событий;
- в логах обработки source maps;
- в личном кабинете.

## Npm-пакеты и совместимость с Sentry

### Решено: совместимость уровня 3

Поддерживаем:

1. знакомые имена функций;
2. совместимые TypeScript-типы для выбранной части API;
3. формат событий и Envelope Sentry.

Публикуются отдельные пакеты:

- **@getexception/browser** для SPA без React. Его публичный API совместим с выбранной частью **@sentry/browser**;
- **@getexception/react** для React SPA. Его публичный API совместим с выбранной частью **@sentry/react** и включает React ErrorBoundary;
- **@getexception/cli** для загрузки source maps. Он не заявляет полную совместимость с sentry-cli.

Мы не переписываем самостоятельно перехват ошибок и разбор browser stack trace. Пакет `@getexception/browser` использует внутри закреплённую major-версию официального MIT-лицензированного `@sentry/browser`, но включает только проверенные возможности и безопасные настройки GetException. Пакет `@getexception/react` зависит от `@getexception/browser` и добавляет React integration из закреплённой версии `@sentry/react`.

Миграция существующего приложения выглядит как одно осознанное изменение импорта:

```ts
- import * as Sentry from '@sentry/react';
+ import * as Sentry from '@getexception/react';
```

Для SPA без React замена выглядит так:

```ts
- import * as Sentry from '@sentry/browser';
+ import * as Sentry from '@getexception/browser';
```

Поддерживаемая поверхность MVP:

```ts
init();
captureException();
captureMessage(); // только error/fatal
setTag();
setTags();
setUser(); // только безопасный анонимный id
addBreadcrumb(); // только безопасная ограниченная схема
withScope();
flush();
```

`@getexception/react` поддерживает тот же общий API и дополнительно экспортирует `ErrorBoundary`.

Неизвестная или неподдерживаемая функция возвращает документированную ошибку либо явно описанное no-op поведение. Поддерживаемая версия Sentry API и отличия документируются. Контрактные тесты запускают официальную закреплённую версию SDK против нашего endpoint.

Пример подключения:

```ts
import * as GetException from "@getexception/react";

GetException.init({
  dsn: import.meta.env.VITE_GETEXCEPTION_DSN,
  release: import.meta.env.VITE_RELEASE,
  environment: import.meta.env.MODE,
});
```

Настройка должна занимать одну небольшую вставку в entry point. DSN не считается секретом и может быть build-time переменной SPA.

Безопасность пакета:

- наружу экспортируется только поддерживаемое подмножество options, а не весь BrowserOptions без ограничений;
- sendDefaultPii, replay, tracing, browser sessions и attachment APIs недоступны;
- пользовательский beforeSend, если будет поддержан, выполняется до финального sanitizer и не может вернуть запрещённые поля;
- transport отправляет только на HTTPS endpoint из DSN через `fetch` с `credentials: 'omit'` и `referrerPolicy: 'no-referrer'`, не добавляет Authorization и не использует `sendBeacon`;
- сетевые и serialization-ошибки поглощаются и при необходимости выводятся только в opt-in debug mode разработки;
- package import не запускает сбор или отправку до явного init;
- shutdown/flush имеет короткий ограниченный timeout;
- рекомендуемая CSP наблюдаемого SPA добавляет только домен ingest в connect-src.

Публикация пакета является критической границей: скомпрометированный SDK выполнялся бы внутри наблюдаемого SPA ещё до серверной очистки. Поэтому изменения SDK и release workflow требуют независимого review, приложения закрепляют проверенную версию, а CI проверяет provenance и фактический состав опубликованного tarball.

### Публикация npm-пакетов

Все npm package names в monorepo используют организацию `@getexception`. Пакеты `@getexception/browser`, `@getexception/react` и `@getexception/cli` публикуются как public packages, а внутренние пакеты помечаются `private: true`. Для публикации используется переменная `NPM_TOKEN`:

- локально значение хранится только в корневом `.env`, который не добавляется в Git;
- `.env.example` содержит пустую строку `NPM_TOKEN=` без секрета;
- в GitHub Actions значение хранится в GitHub Secret с именем `NPM_TOKEN`;
- workflow передаёт токен только job публикации и создаёт временную настройку npm с `${NPM_TOKEN}`;
- токен имеет минимальные права на публикацию пакетов организации `@getexception`, регулярно заменяется и никогда не попадает в Docker image, runtime-конфигурацию сервера, логи или build artifact.

CI выполняет `npm publish --provenance` с `NPM_TOKEN`, проверяет опубликованные tarball и затем устанавливает оба SDK из npm registry в чистые fixture-приложения.

### Поддерживаемые браузеры

MVP поддерживает последние две основные версии Chrome, Edge и Firefox, а также текущую и предыдущую основные версии Safari на момент выпуска SDK. Internet Explorer не поддерживается. Конкретная матрица публикуется вместе с каждой major-версией пакета и проверяется автоматическими browser tests.

## Вход, регистрация, команды и роли

### Первоначальная настройка

При первом открытии новой установки личный кабинет показывает только мастер системной настройки. До его завершения вход, приглашения и приём событий отключены.

Мастер требует одноразовый bootstrap-токен, который установщик создал на сервере и показал оператору. Пользователь задаёт:

1. основной домен установки, например `errors.example.com`;
2. email и пароль первого root-пользователя;
3. TOTP для root-пользователя через Google Authenticator, 1Password или другое совместимое приложение;
4. recovery-коды, которые нужно сохранить вне сервера.

Домен задаёт канонические адреса `https://<domain>` для кабинета и `https://ingest.<domain>` для приёма событий. Сервер проверяет синтаксис и точное совпадение настроенного host, не принимает значение из заголовков `Host` или `Forwarded-Host` и использует отдельный локальный режим для `localhost`.

Root-пользователь является первым участником с ролью Owner. Это понятие не связано с Linux root, PostgreSQL superuser или правами Docker host. Создание системной конфигурации, рабочего пространства, учётной записи, Owner membership и TOTP выполняется одной транзакцией. После успешного завершения bootstrap-токен уничтожается, а `/setup` больше не позволяет повторную настройку.

### Как устроено в Sentry и что мы берём

В Sentry учётная запись человека отделена от доступа к организации. Администратор приглашает человека по email, сразу указывает роль организации и команды. Команды связаны с проектами; роль и членство в командах определяют доступ. Sentry также умеет разрешать свободное вступление в команды, но для нашего закрытого сервиса этот режим не нужен.

Мы берём сам принцип, но уменьшаем число сущностей:

- одна установка — одна компания и одно рабочее пространство;
- Owner приглашает участника;
- приглашение заранее содержит роль и команды;
- участник входит по email и паролю;
- Developer и Viewer видят проекты только своих команд;
- Owner видит все команды и проекты;
- свободного вступления в команды нет.

### Учётная запись и участие — разные вещи

Учётная запись отвечает на вопрос «кто вошёл». Участие отвечает на вопрос «куда ему разрешено войти». Даже правильно введённый пароль не даёт доступа без активного участия в рабочем пространстве.

Приглашение:

1. создаётся только Owner после TOTP step-up не старше пяти минут;
2. содержит нормализованный email, роль Developer или Viewer и назначенные команды;
3. не может назначить роль Owner;
4. имеет отдельный внутренний ID и случайный одноразовый токен из 32 байт;
5. хранит только SHA-256 хеш токена;
6. действует 48 часов и имеет явное состояние `pending`, `accepted`, `revoked` или `expired`;
7. имеет не более одной записи `pending` на пару workspace и нормализованный email;
8. после принятия становится недействительным;
9. может быть повторно отправлено или отозвано Owner после свежего TOTP step-up.

Повторная отправка сохраняет внутренний ID приглашения, но создаёт новый токен и новый срок. Старый токен сразу перестаёт работать. Запись mail outbox получает новую revision, поэтому worker не должен отправить письмо со старым токеном после повторной отправки. Отзыв меняет состояние на `revoked` и отменяет необработанное письмо. Многоразовые ссылки без привязки к email запрещены.

Страница приглашения получает токен из URL fragment и передаёт его серверу в теле POST-запроса. Токен не должен попадать в request target, access log, `Referer`, analytics или audit metadata. Ответ предварительного просмотра имеет `Cache-Control: no-store`, показывает название workspace, имя пригласившего, роль, команды и маскированный email. Ответ не сообщает, существует ли уже учётная запись.

Если приглашённый уже имеет учётную запись, он сначала входит обычным способом. Сервер требует подтверждённый email, который совпадает с email приглашения после нормализации. Если учётной записи нет, сервер по действующему invitation token отправляет отдельное одноразовое подтверждение на email из приглашения. До перехода по ссылке подтверждения сервер не принимает пароль и не создаёт Account. После подтверждения сервер выдаёт короткую registration session в `HttpOnly` cookie. Только эта сессия открывает форму имени и пароля. Email берётся из приглашения и не может быть заменён клиентом.

Окончательное принятие выполняется одной транзакцией. Сервер блокирует приглашение, повторно проверяет состояние, срок и email, создаёт `member` и записи `team_member`, затем переводит приглашение в `accepted` и очищает хеш токена. Уникальные ограничения не позволяют двум параллельным запросам принять одно приглашение или создать второе участие. Если человек уже является участником, приглашение не меняет его роль или команды. Owner выполняет такое изменение отдельной операцией с audit event.

Better Auth остаётся источником учётных записей, сессий и участия в organization. Для organization plugin включается `requireEmailVerificationOnInvitation`. В версии 1.6.23 стандартное приглашение принимает invitation ID и поддерживает один необязательный `teamId`. Требования GetException к хешированному bearer token, нескольким командам и transactional mail outbox реализуются узким серверным слоем и таблицей `invitation_team`, а не ослабляются ради стандартного route. Стандартные create, accept, reject и cancel routes Better Auth не публикуются напрямую. Внутренний invitation ID никогда не считается секретом и не позволяет обойти проверку нашего token.

Сервис отправляет приглашение по email через настроенный SMTP. Эта же почтовая доставка используется для безопасного восстановления пароля. Создание токена и запись mail outbox выполняются в одной транзакции. `worker-mail` получает записи короткой lease через `FOR UPDATE SKIP LOCKED`, повторяет временные ошибки с ограниченным backoff и после обработки заменяет payload безопасным маркером без исходного токена. Письма авторизации являются служебными сообщениями и не означают добавление продуктовых уведомлений об ошибках.

Уточнение первоначального запуска, 10 сентября 2026 года: установка может работать без почты с `MAIL_ENABLED=false`. Owner создаётся через bootstrap и TOTP, входит по паролю и TOTP/recovery code, управляет проектами и читает ошибки без SMTP. Приглашения временно недоступны в UI и серверном API, кроме отзыва уже созданных приглашений; обход подтверждения email или выдача invitation tokens вручную не допускаются. `worker-mail` сохраняет health endpoints, но не создаёт SMTP transport и не забирает outbox, поэтому выключение доставки не расходует попытки и не уничтожает ожидающие письма. Новая установка без SMTP выбирает этот режим автоматически. Установки без нового флага сохраняют прежнее поведение с включённой почтой. Подключение SMTP и `MAIL_ENABLED=true` требует перезапуска web и worker-mail с прежними секретами и базой; повторная регистрация Owner не нужна.

Уточнение реализации приглашений, 8 сентября 2026 года: поля проверки приглашения, подтверждения email и registration session содержат только SHA-256 хеши. Чтобы worker мог доставить письмо, его payload хранится отдельно в outbox с AES-256-GCM и независимым `MAIL_ENCRYPTION_KEY`, доступным только web и worker-mail. AAD связывает ciphertext с ID письма и revision; повторная отправка заменяет ciphertext, завершение или отмена очищает его. Перед SMTP worker повторно блокирует актуальную revision outbox на время ограниченной отправки: отзыв и повторная отправка сериализуются с уже начавшейся доставкой. SMTP даёт доставку как минимум один раз: после сбоя между отправкой и commit возможен дубль письма, но не повторное получение доступа. Уже доставленную ссылку отзыв и новая revision немедленно делают недействительной. Локальный Mailpit принимает только тестовые письма, слушает loopback и не пересылает их наружу.

### Вход по email и паролю

- пароль никогда не хранится в открытом виде;
- для хеширования используется Argon2id с параметрами, проверенными для production-сервера;
- минимальная длина — 12 символов, максимальная — 128;
- сложные искусственные правила вида «обязательна одна заглавная и один знак» не вводятся;
- известные скомпрометированные пароли отклоняются локальным или безопасным проверенным способом;
- ответы входа и восстановления не раскрывают, существует ли email;
- число попыток ограничивается по IP и учётной записи;
- после смены или сброса пароля остальные сессии отзываются.

Ссылка сброса пароля одноразовая, хранится в виде хеша и также имеет короткий срок действия. После смены пароля она уничтожается, а существующие сессии отзываются.

### Двухфакторная защита

Для Owner после пароля обязателен второй фактор TOTP. Это шестизначный код из Google Authenticator, 1Password или другого приложения, которое поддерживает стандарт TOTP. Для Developer и Viewer TOTP доступен в настройках аккаунта, но в MVP остаётся добровольным.

Настройка TOTP состоит из двух шагов. Сначала сервер повторно проверяет пароль, создаёт случайный 160-битный secret и сохраняет его как pending credential. Ответ с `otpauth://` URI и ручным secret получает `Cache-Control: no-store`. Затем сервер проверяет первый код и одной транзакцией переводит credential в active. Незавершённая настройка не включает второй фактор.

При первоначальном setup постоянной учётной записи ещё нет. Первым фактором служат действующий bootstrap token и введённый пароль, который сразу хешируется. До подтверждения TOTP данные остаются частью ограниченной setup-сессии. Финальная транзакция создаёт системную настройку, root-пользователя, Owner membership, active TOTP credential и recovery codes, после чего удаляет setup-сессию и bootstrap token.

Pending и active TOTP secrets шифруются на уровне приложения через AES-256-GCM со случайным nonce. В authenticated additional data входят user ID и состояние credential, поэтому ciphertext нельзя незаметно переставить другому пользователю или между pending и active. Формат ciphertext имеет версию. Отдельный 32-байтный ключ шифрования обязателен в production, не доступен ingest и worker и входит в зашифрованный backup секретов. При отсутствии или неверной длине ключа web не открывает HTTP port.

Сервер принимает только шестизначный код из текущего 30-секундного окна или одного соседнего окна с каждой стороны. Сравнение выполняется за постоянное время. Номер последнего принятого окна хранится в credential и обновляется под блокировкой строки в одной транзакции с созданием сессии или step-up. Один код нельзя использовать второй раз, включая два параллельных запроса.

При настройке создаются одноразовые recovery-коды. Они показываются только один раз, хранятся в виде хешей и после использования становятся недействительными. Developer или Viewer отключает TOTP только после ввода текущего пароля и свежего TOTP или recovery-кода. Отключение записывается в audit log и отзывает все сессии. Owner не может оставить аккаунт без активного второго фактора. Он может только заменить credential или пройти утверждённое восстановление с обязательной повторной настройкой.

GetException проверяет пароль и TOTP самостоятельно. Сессия Owner не становится полноценной до успешной проверки второго кода.

Better Auth остаётся системой учётных записей и сессий. Для Owner trusted-device режим отключён, а сервер отклоняет попытку создать такую сессию. Хранилище 2FA проверяется отдельно. Если плагин не обеспечивает шифрование secret, защиту от повторного временного окна или хешированное одноразовое использование recovery-кодов, GetException добавляет узкий серверный слой и отдельные таблицы вместо ослабления этих требований.

Ответы login challenge, TOTP setup, status и step-up нельзя кэшировать. Rate limit считается в PostgreSQL одновременно по IP и нормализованной учётной записи. Audit log разделяет успешные и неуспешные password, TOTP, step-up и recovery действия, но не содержит password, secret, TOTP code или recovery code. Email OTP не используется как запасной второй фактор Owner.

Сброс TOTP по одному письму запрещён, иначе email стал бы обходом второго фактора. Если recovery-коды потеряны, reset подтверждает другой Owner своей свежей сессией и TOTP. Для единственного Owner используется отдельный длинный одноразовый offline recovery secret, созданный при bootstrap и находящийся у оператора сервера. Reset отзывает все сессии аккаунта и требует заново настроить TOTP. Перед production рекомендуется создать минимум двух Owner и проверить recovery-процедуру.

### Сессия

Сессия хранится в host-only cookie с префиксом `__Host-`, `Secure`, `HttpOnly`, `Path=/`, без атрибута `Domain` и с подходящим `SameSite`. Cookie принадлежит только origin личного кабинета и физически не отправляется на отдельный origin ingest. Токены входа не кладутся в localStorage. Изменяющие запросы защищаются от CSRF проверкой token/Origin и Content-Type. Сессии имеют срок бездействия, абсолютный срок жизни, ротацию после входа и возможность индивидуального или общего отзыва.

Смена пароля, email, MFA, роли или membership отзывает старые сессии либо заставляет сервер немедленно переоценивать права. Сессия хранит `mfa_verified_at`. Смена email, управление TOTP, создание CI-токена, замена DSN, повышение до Owner и удаление проекта требуют password и TOTP step-up не старше пяти минут.

Root-пользователь создаётся в мастере первоначальной настройки через одноразовый bootstrap URL/token, показанный только после установки. После создания root-пользователя bootstrap-токен уничтожается.

### Решено: команды

- участник может состоять в нескольких командах;
- проект может быть доступен нескольким командам;
- у каждого проекта должна быть хотя бы одна команда;
- свободного самостоятельного вступления в команды нет;
- Owner создаёт команды, приглашает участников и связывает команды с проектами;
- Owner видит все проекты независимо от собственного членства;
- Developer и Viewer видят только проекты, связанные хотя бы с одной их командой;
- роль одна на всё рабочее пространство, а не отдельная для каждой команды.

Таким образом, роль определяет, что человек может делать, а команды — с какими проектами он может это делать.

### Решено: три роли

| Действие                              | Owner |      Developer      |       Viewer        |
| ------------------------------------- | :---: | :-----------------: | :-----------------: |
| Смотреть проекты, ошибки и статистику |  все  | только своих команд | только своих команд |
| Искать и фильтровать                  |  да   |         да          |         да          |
| Помечать ошибку решённой/открытой     |  да   |         да          |         нет         |
| Создавать и менять проекты            |  да   |         нет         |         нет         |
| Менять origin и публичный DSN         |  да   |         нет         |         нет         |
| Создавать CI-токены                   |  да   |         нет         |         нет         |
| Управлять участниками и ролями        |  да   |         нет         |         нет         |
| Создавать команды и назначать проекты |  да   |         нет         |         нет         |
| Менять хранение и квоты               |  да   |         нет         |         нет         |
| Удалять проект или данные             |  да   |         нет         |         нет         |

Разрешено несколько Owner. Последнего активного Owner нельзя удалить или понизить в роли. Для Developer и Viewer сервер проверяет одновременно роль и членство в команде, которой доступен проект. Проверка выполняется для каждой операции и каждого объекта; скрытая кнопка в интерфейсе защитой не является.

## Разрешённые origin и окружения

Для каждого проекта задаются точные origin: протокол + домен + порт. Например:

```text
https://app.example.com
https://staging-app.example.com
http://localhost:5173
```

Правила:

- звёздочка в production запрещена;
- origin сравнивается после строгого разбора URL, а не через endsWith;
- example.com.evil.test не совпадает с example.com;
- схема http/https и порт являются частью origin;
- localhost разрешается отдельно и по умолчанию только для окружения development;
- запрос браузера с присутствующим, но неподходящим Origin отклоняется;
- отсутствие Origin не доказывает доверие и обрабатывается отдельным более строгим rate limit.

Для разрешённого браузера ingest возвращает Access-Control-Allow-Origin только с точным полученным origin и Vary: Origin. Access-Control-Allow-Credentials не включается: npm-пакет не должен отправлять cookie. Caddy удаляет присланные клиентом proxy-заголовки и сам устанавливает доверенный адрес источника, чтобы rate limit нельзя было обойти поддельным X-Forwarded-For.

Окружения MVP: **production**, **staging**, **development**. Один Project соответствует одному логическому SPA, а не одному домену или окружению.

## Обработка и группировка

Приёмник быстро записывает безопасное событие в PostgreSQL inbox и отвечает SDK, не ожидая тяжёлой обработки. Worker забирает записи небольшими пакетами:

1. окончательно нормализует данные;
2. находит source map;
3. восстанавливает исходный stack trace;
4. вычисляет отпечаток;
5. находит или создаёт группу ошибок;
6. сохраняет событие;
7. обновляет счётчики;
8. планирует удаление по retention policy.

Очередь хранит число попыток, время следующей попытки и состояние dead letter. Обработка идемпотентна по паре project ID + event ID, поэтому повторный запрос или retry не создаёт вторую запись.

Один worker image запускается в трёх режимах. `worker-events` обрабатывает новые события и может иметь несколько реплик. `worker-retention` запускается в одном экземпляре и удаляет данные короткими пакетами. `worker-mail` получает transactional outbox и доставляет приглашения и password reset через SMTP. Такое разделение не позволяет очистке истории или всплеску ошибок задерживать служебные письма.

### Решено: базовый отпечаток

По умолчанию отпечаток строится из:

- типа исключения;
- нормализованного сообщения;
- нескольких верхних значимых stack frames из кода приложения;
- исходных файлов и функций после применения source maps, если они доступны.

Из сообщения убираются изменяющиеся идентификаторы, UUID, длинные числа и очевидные технические значения, чтобы «Entity 123 not found» и «Entity 456 not found» не становились разными группами.

Пакет может передать явный fingerprint, но только как ограниченный массив коротких безопасных строк. Сервер всё равно проверяет его размер и содержимое.

Когда новое событие попадает в группу со статусом resolved, группа автоматически возвращается в open, получает признак regression и время повторного появления.

## Релизы и source maps

Source map нужен потому, что production JavaScript обычно сжат. Без него кабинет покажет **a() в app.8f3.js:1:27192**; с ним — исходную функцию, файл и строку TypeScript.

### Идентификатор релиза

MVP использует:

```text
<project-slug>@<full-git-commit-sha>
```

Git tag, номер приложения или имя ветки можно хранить как отображаемые поля, но они не заменяют неизменяемый SHA. Тот же release передаётся npm-пакету при сборке SPA и CLI при загрузке артефактов.

### Решено: свой небольшой CLI и Debug ID

Создаём **@getexception/cli** только с необходимыми командами. Полную копию sentry-cli не делаем.

Основной CI-сценарий:

1. SPA собирается;
2. CLI находит сгенерированные .js и .map;
3. CLI записывает одинаковый случайный Debug ID в пару JavaScript + source map;
4. изменённые production-файлы идут в деплой;
5. source maps и метаданные загружаются в GetException;
6. runtime SDK добавляет Debug ID в событие;
7. Worker выбирает точную карту по project + Debug ID, а release использует для фильтрации и контроля.

Debug ID надёжнее одного имени файла или release: он однозначно связывает конкретный сжатый файл с конкретной картой.

### Секретный CI-токен

Токен загрузки source maps:

- генерируется случайно;
- показывается один раз;
- хранится в GetException только в виде хеша;
- находится только в secret storage CI;
- привязан к одному проекту;
- может только загружать артефакты;
- не читает ошибки и настройки;
- отзывается и заменяется;
- никогда не попадает в React bundle.

Upload endpoint дополнительно:

- принимает только HTTPS и Authorization Bearer;
- ограничивает суммарный размер релиза и число файлов;
- проверяет Debug ID, release, checksum и допустимые расширения;
- не доверяет имени и пути файла от клиента;
- запрещает абсолютные пути и выход из каталога через две точки;
- не распаковывает произвольный архив без проверки числа файлов и распакованного размера;
- атомарно публикует набор карт только после полной проверки;
- не предоставляет API скачивания исходных source maps в MVP.

Имена хранения создаёт сервер; присланный путь не используется напрямую. Запрещаются symlink, абсолютные пути и выход из staging-каталога. Разбор карты выполняется в Worker без root, shell, internet egress и доступа к auth-таблицам, с отдельными CPU/memory/time limits. Ошибка или OOM-защита одного артефакта не останавливает очередь. CLI не строит shell-команды из имён файлов. После успешной загрузки CI проверяет, что `.map` отсутствуют в публичном deploy artifact.

### Хранение

В первой одно-серверной версии:

- метаданные артефактов лежат в PostgreSQL;
- сами .map лежат в закрытом именованном Docker volume;
- Caddy и Next.js не раздают каталог артефактов публично;
- доступ идёт через внутренний интерфейс хранения;
- позже volume можно заменить S3-совместимым хранилищем без изменения модели событий.

Source maps могут содержать исходный код и считаются конфиденциальными. В принятом упрощённом backup они не копируются; восстановление возможно только повторной загрузкой сохранённых CI-артефактов.

### Если загрузка source maps не удалась

После нескольких повторов неудача загрузки не должна навсегда блокировать production-деплой приложения: ошибка мониторинга не должна мешать выпустить срочное исправление. CI сохраняет подготовленный архив как закрытый артефакт, показывает явное предупреждение и позволяет повторить загрузку без пересборки. В GetException релиз получает статус **source maps missing**.

Если карта пришла после события, Worker повторно обрабатывает неразрешённые stack frames этого релиза и при необходимости пересчитывает отпечаток. Слияние или разделение уже видимых групп записывается в audit log и отображается в истории группы.

Основные таблицы:

| Таблица               | Назначение                                                             |
| --------------------- | ---------------------------------------------------------------------- |
| system_setting        | домен установки, версия и признак завершённой первоначальной настройки |
| bootstrap_token       | хеш одноразового токена первоначальной настройки и срок действия       |
| workspace             | одна граница доступа установки; соответствует organization Better Auth |
| user                  | email и состояние учётной записи                                       |
| auth_account          | Argon2id password credential                                           |
| verification          | одноразовые email, invitation registration и password-reset записи     |
| mail_outbox           | надёжная очередь приглашений и password reset                          |
| invitation            | ID, email, роль, состояние, срок и хеш одноразового токена             |
| invitation_team       | снимок команд, атомарно назначаемых при принятии приглашения           |
| mfa_credential        | versioned pending/active TOTP ciphertext, последний принятый counter   |
| recovery_code         | хеш одноразового recovery-кода                                         |
| member                | роль и состояние участия в workspace                                   |
| session               | серверные сессии участников                                            |
| team                  | команда внутри workspace                                               |
| team_member           | членство участника в командах                                          |
| project               | настройки наблюдаемого SPA                                             |
| project_team          | команды, которым доступен проект                                       |
| project_ingestion_key | хеши публичных ключей и сроки ротации                                  |
| project_origin        | разрешённые origin                                                     |
| source_map_token      | хеши секретных CI-токенов                                              |
| release               | неизменяемые сборки                                                    |
| source_artifact       | Debug ID, метаданные и закрытый путь к карте                           |
| event_inbox           | ограниченная надёжная очередь                                          |
| issue                 | группа ошибок, статус, отпечаток и счётчики                            |
| error_event           | отдельное очищенное событие                                            |
| project_daily_stat    | дневные счётчики принятых, отброшенных и уникальных событий            |
| audit_log             | входы и важные административные изменения                              |

Все строки проекта содержат project ID; уникальные ключи и запросы учитывают его. Событие нельзя получить только по публичному UUID без серверной проверки членства и роли.

Разрешённые поля события хранятся типизированными колонками. Stack frames, безопасные breadcrumbs и tags допускаются в ограниченных JSONB-полях с проверкой схемы до записи. Исходный непроверенный payload не хранится.

Минимальные индексы:

- issue по project ID + status + last seen;
- error event по issue ID + received at;
- release по project ID + release name;
- source artifact по project ID + Debug ID;
- inbox по status + next attempt at;
- уникальный project ID + event ID для идемпотентности;
- уникальный pending invitation по workspace ID + normalized email;
- уникальный token hash среди активных приглашений;
- уникальные workspace ID + user ID для member, invitation ID + team ID и member ID + team ID.

Удаление по retention выполняется короткими пакетами, чтобы не блокировать рабочие запросы. Партиционирование по времени добавляется только при подтверждённой необходимости.

Если приложение передало безопасный opaque end-user ID, Worker сохраняет не исходное значение, а HMAC с отдельным project-scoped ключом. Это позволяет считать затронутых людей, но не показывать и не сопоставлять исходный идентификатор между проектами.

## Разделение серверных прав

- ingest может прочитать минимальную конфигурацию приёма проекта и добавить строку в inbox;
- ingest не может читать события, участников, сессии и source maps;
- worker-events читает inbox, пишет события/группы и читает source maps;
- worker-mail читает только mail outbox и получает SMTP credentials;
- web работает с данными кабинета по правам участника;
- миграции используют отдельную повышенную роль только на время deploy;
- PostgreSQL не публикует порт в интернет;
- внутренние Docker-сети отделяют публичный proxy от БД.

Даже при ошибке в публичном обработчике минимальные права уменьшают объём доступных данных.

Конкретные PostgreSQL-роли:

| Роль                   | Минимальные права                                                                                            |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| `getexception_migrate` | DDL только во время deploy; не используется runtime-процессами                                               |
| `getexception_ingest`  | SELECT только ограниченного view активных project/key/origin/quota и INSERT только разрешённых колонок inbox |
| `getexception_worker`  | очередь, issue, error_event, stats и метаданные source maps; без auth/session/recovery tables                |
| `getexception_mail`    | claim и обновление mail outbox; без чтения password, TOTP и error events                                     |
| `getexception_web`     | кабинет, auth и проекты; без DDL и superuser-прав                                                            |
| `getexception_backup`  | чтение только для согласованного `pg_dump`; без записи                                                       |

У всех runtime-ролей: `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOBYPASSRLS`, разные случайные SCRAM-SHA-256 пароли, connection/statement/lock/idle-transaction limits. Права `PUBLIC` на прикладные схемы отзываются. CI подключается каждой ролью и проверяет как разрешённые операции, так и ожидаемый `permission denied`.

Обычные запросы выполняются Prisma Client. `$queryRawUnsafe`, `$executeRawUnsafe`, `Prisma.raw` с пользовательскими данными и конкатенация SQL запрещены. Необходимый `FOR UPDATE SKIP LOCKED` является фиксированным tagged-template запросом с параметрами. Динамические сортировки и поля выбираются сервером из allow-list, а не вставляются из HTTP-параметра.

PostgreSQL RLS рассматривается как последующее усиление, а не как замена проверкам приложения. Он включается только после отдельного прототипа корректного project context в каждой транзакции с connection pool; владельцы таблиц и роли с `BYPASSRLS` не используются для обычных запросов.

## Защита личного кабинета и API

- все разрешения проверяются на сервере;
- идентификатор проекта или события не является правом доступа;
- HTML из сообщений ошибок не исполняется;
- сообщения и stack trace выводятся как текст;
- запрещено использовать `dangerouslySetInnerHTML`, небезопасный markdown, runtime-шаблоны или URL события для `href/src`;
- включается строгая Content Security Policy с nonce, без `unsafe-inline`, с `object-src 'none'`, `base-uri 'none'` и `frame-ancestors 'none'`;
- API возвращает JSON с `X-Content-Type-Options: nosniff`;
- изменяющие запросы требуют CSRF-защиту и подходящий Content-Type;
- чувствительные ответы используют Cache-Control: no-store;
- секретные токены показываются только при создании;
- административные действия попадают в append-only audit log;
- ошибки самого GetException не должны содержать входные payload и секреты;
- production debug endpoints выключены.

Ключи `__proto__`, `prototype` и `constructor` рекурсивно отклоняются. Входной объект не объединяется с настройками через deep merge/Object.assign/spread. Логи не включают raw payload; control/ANSI characters удаляются, а причины отказа выбираются из серверного enum.

## Исходящий трафик и запрет утечки наружу

После приёма события GetException не отправляет его в Sentry, аналитику, AI-сервис или другую третью систему. Source-map обработка, группировка, поиск и статистика выполняются локально.

Разрешённые внешние соединения:

| Процесс                          | Куда может обращаться       | Какие данные уходят                                        |
| -------------------------------- | --------------------------- | ---------------------------------------------------------- |
| Caddy                            | ACME-провайдер сертификатов | доменное имя установки                                     |
| worker-mail                      | настроенный SMTP            | приглашение или восстановление пароля, без ошибок проектов |
| backup                           | настроенное S3              | только заранее зашифрованный PostgreSQL dump               |
| ingest                           | никуда во внешний интернет  | ничего                                                     |
| worker-events и worker-retention | никуда во внешний интернет  | ничего                                                     |

Шрифты, JavaScript и CSS кабинета отдаются с нашего домена, без CDN и внешних analytics scripts. Npm-пакет отправляет данные только на origin из настроенного DSN и не содержит telemetry самого пакета.

Docker networks и firewall ограничивают исходящий трафик по возможности инфраструктуры. Ingest, worker-events и worker-retention не получают SMTP или S3 credentials. Только worker-mail получает SMTP credentials. Ключ шифрования backup не хранится в S3. Добавление нового внешнего получателя данных требует отдельного security review и изменения ADR.

HTTP client не должен автоматически ходить по URL, полученному из события. Это исключает SSRF через подложенный filename, source-map URL или пользовательское поле.

## Производительность и хранение

Расчётный запас для примерно 2 000 конечных пользователей в день:

- до 100 000 принятых событий в сутки;
- один проект принимает в среднем до 20 событий/секунду с кратким всплеском до 50;
- один IP принимает в среднем до 10 событий/секунду с кратким всплеском до 30;
- стандартная квота проекта — 25 000 событий в сутки;
- отдельные события хранятся 30 дней;
- группы, их статусы и агрегированные счётчики — бессрочно до удаления проекта;
- события сверх квоты явно отклоняются и учитываются в счётчике;
- SDK не блокирует работу SPA, если сервис недоступен;
- отправка выполняется асинхронно с коротким timeout;
- сбой мониторинга никогда не ломает пользовательское приложение.

На таком объёме PostgreSQL достаточно и как базы, и как начальной надёжной очереди. Redis добавляется только по результатам нагрузки или production-метрик, а не заранее.

Перед приёмкой запускаются тесты:

- обычная постоянная нагрузка;
- всплеск 50/с;
- одинаковые ошибки;
- максимально допустимые события;
- malformed Envelope;
- медленные соединения;
- переполнение inbox;
- одновременная обработка несколькими worker.

## Удаление проекта

Удаление выполняется в два этапа:

1. сразу отключаются публичные ключи DSN и секретные CI-токены;
2. проект, его ошибки и source maps скрываются от Developer и Viewer;
3. в течение 7 дней Owner может восстановить проект;
4. через 7 дней Worker окончательно удаляет события, группы, релизы, ключи и source maps;
5. audit log сохраняет сам факт удаления без содержимого удалённых событий.

Во время периода восстановления ingest не принимает новые события проекта. После окончательного удаления старые DSN и токены нельзя восстановить. Если данные присутствуют в резервной копии, они исчезают вместе с окончанием срока хранения этой копии и не должны возвращаться в рабочую систему при обычном restore.

## Что берём из Selfchecks, Selflify и AppNotes

Selfchecks, Selflify и AppNotes служат источниками проверенных приёмов для структуры репозитория, аутентификации, установки и выпуска. Подробный разбор конкретных файлов, ограничений и лицензий находится в [отчёте по референсным проектам](./REFERENCE-PROJECTS.md).

### Решения из Selfchecks

GetException использует следующие решения из Selfchecks:

- корневые Yarn workspaces для `apps/*` и `packages/*`, общие scripts и закреплённую версию Yarn;
- `nodeLinker: node-modules`, поэтому Plug and Play не используется;
- единые команды format, lint, typecheck, test и build из корневого `package.json`;
- `yarn install --immutable` в CI и сборке Docker image;
- отдельные приложения web и worker, отдельные Docker targets и отдельные образы в GHCR;
- одноразовый сервис migrate, после успешного завершения которого запускаются runtime-сервисы;
- настраиваемую в разумных границах параллельность worker без пересборки image;
- корректное завершение worker по SIGINT и SIGTERM: перестать брать новые задачи, закончить или безопасно освободить текущие и закрыть соединения;
- сериализацию production release через GitHub Actions concurrency;
- проверку, что ветка `stable` не изменилась во время создания автоматического release commit;
- теги Docker image `stable` и `sha-<commit>`, при этом production deploy использует конкретный SHA или digest;
- публикацию npm-пакетов с `NPM_TOKEN` и provenance, проверку существующей версии и ожидание появления пакета в registry;
- установку опубликованного npm tarball в чистый fixture вместо проверки только workspace-сборки;
- bootstrap bundle с явным списком файлов и smoke test его структуры и режима `--skip-start`.

В GetException список runtime-образов расширяется до web, ingest и worker. Корневая команда `yarn checks` объединяет обязательные проверки, чтобы локальный запуск и CI использовали один вход. - установку в отдельный каталог `/opt/getexception` с постоянным подкаталогом `runtime`;

### Решения из AppNotes

GetException использует следующие решения из AppNotes:

- двухэтапную настройку TOTP через pending credential и подтверждение первого кода;
- шифрование TOTP secret на уровне приложения через versioned AES-256-GCM ciphertext с привязкой к user ID и состоянию credential;
- защиту от повторного использования TOTP code через last accepted counter и транзакционную блокировку;
- `mfa_verified_at` в серверной сессии и step-up не старше пяти минут для опасных операций;
- `Cache-Control: no-store` для ответов MFA и отдельные audit events для успехов и отказов;
- общие auth rate limits в PostgreSQL по хешированным IP и account identifiers;
- полный lifecycle приглашения с привязкой к нормализованному email, ротацией токена, проверкой подтверждённого email и транзакционным созданием участия;
- transactional mail outbox для приглашений и password reset с отдельным worker, lease, `SKIP LOCKED`, ограниченными повторами и удалением чувствительного payload после обработки;
- исполняемый architecture check, который запрещает зависимости между несовместимыми workspaces;
- fail-closed production startup при отсутствии обязательного секрета, неприменённой миграции или недоступной обязательной зависимости.

AppNotes имеет `UNLICENSED` в корневом package manifest. GetException использует только проверяемое поведение и тестовые случаи, а реализацию пишет заново или получает из выбранных зависимостей. ### Что не переносим

GetException не переносит решения, которые противоречат принятой архитектуре:

- Redis из Selfchecks, потому что очередь MVP хранится в PostgreSQL inbox;
- Cloudflare API token и автоматическое управление DNS из Selflify, потому что GetException принимает готовый домен и не управляет DNS-провайдером;
- автоматическую установку Docker через удалённый shell script, потому что bootstrap проверяет Docker и выводит отдельную инструкцию по установке;
- получение SSH host key через `ssh-keyscan` без заранее проверенного fingerprint;
- общую роль PostgreSQL для всех runtime-процессов;
- копирование всего repository checkout на production-сервер вместо версионированного bootstrap bundle и Docker images;
- постоянный setup token после создания root-пользователя;
- изменяемый тег `stable` как единственный идентификатор production image;
- in-memory rate limit для входа как единственное общее ограничение между репликами;
- проверку `service_started` вместо настоящего readiness endpoint;
- безусловный `docker system prune -af`, который может удалить image, нужный для отката;
- email OTP из AppNotes как запасной второй фактор Owner;
- trusted-device cookie, которая позволяет Owner пропускать TOTP при новой сессии;
- более короткий пароль после включения MFA;
- многоразовые invitation links без привязки к email;
- invitation token в query string, где он может попасть в историю браузера, access log или `Referer`;
- создание личного workspace или проекта для каждого приглашённого пользователя;
- общую PostgreSQL-роль для API и worker из self-hosted профиля AppNotes.

Selfchecks распространяется под Elastic License 2.0. Поэтому из него берутся архитектурные идеи и проверяемое поведение, но код не копируется без отдельной проверки лицензии и происхождения. Selflify распространяется под MIT, однако его код также не переносится автоматически. AppNotes помечен как `UNLICENSED`, поэтому его код не копируется. Каждое решение должно соответствовать границам безопасности GetException.

Референсные решения считаются требованиями только в том виде, который описан в этом ADR. Изменения в Selfchecks, Selflify или AppNotes автоматически не меняют GetException.

### Решение по авторизации

Референсные проекты используют NextAuth/Auth.js, однако GetException нужны одновременно invitation-only signup, пароль, команды и TOTP. В Better Auth эти функции входят в одну систему, поэтому для нового проекта он уменьшает объём самостоятельно реализуемой security-логики. Google и другие social providers не настраиваются.

Better Auth используется только для подтверждения личности, сессий, приглашений и базовой модели workspace/team. Доступ к конкретному Project всегда дополнительно проверяет наш серверный authorization service; клиентская проверка Better Auth не является достаточной.

Обязательные настройки:

- создание дополнительных organizations/workspaces пользователем запрещено;
- удаление единственного workspace через стандартный auth endpoint запрещено;
- свободная регистрация запрещена проверочным before/database hook;
- активное приглашение может только начать отдельную проверку email, а форма имени и пароля открывается после неё;
- пароль хешируется через настраиваемый Argon2id provider;
- organization plugin использует статические роли Owner, Developer, Viewer и teams;
- organization invitation требует подтверждённый email и истекает через 48 часов;
- 2FA plugin используется для TOTP и recovery-кодов; сервер требует завершённую TOTP-проверку для каждой сессии Owner;
- встроенный rate limit усиливается отдельными правилами для login, reset и TOTP;
- trusted origins содержат только production-домены кабинета;
- invitation/reset URLs строятся из домена, сохранённого при первоначальной настройке, а не из `Host`/`Forwarded-Host`; секретная часть находится в URL fragment, а redirect/return target проходит allow-list;
- self-service endpoints не принимают `role`, `team`, `workspace` или `project` как назначаемые пользователем права;
- telemetry библиотеки выключена;
- ключ шифрования auth поддерживает безопасную ротацию.

Invitation-only flow:

1. страница читает invitation token из URL fragment и передаёт его в POST preview;
2. существующий пользователь входит, после чего сервер проверяет подтверждённый email и принимает приглашение;
3. для нового пользователя active invitation может только отправить отдельную одноразовую ссылку на email из приглашения;
4. переход по ссылке подтверждения создаёт короткую registration session, привязанную к invitation и email;
5. форма имени и пароля доступна только из этой registration session;
6. создание Account, Member, team memberships и погашение Invitation выполняются одной транзакцией;
7. при любой ошибке транзакция полностью откатывается;
8. прямой вызов публичного signup endpoint без registration session получает нейтральный отказ.

### Решение по PostgreSQL

Prisma обслуживает обычные CRUD-запросы и миграции. Для конкурентного получения задач Worker использует параметризованный SQL с PostgreSQL FOR UPDATE SKIP LOCKED внутри короткой транзакции. Это позволяет нескольким Worker не обрабатывать одну запись одновременно.

Значение из события никогда не становится частью текста SQL. CI запрещает unsafe Prisma APIs и проверяет, что динамические sort/filter выбираются только из серверного allow-list.

Миграции:

- генерируются разработчиком и сохраняются в Git;
- просматриваются как SQL в pull request;
- в production выполняются только командой migrate/deploy-контейнера;
- не используют db push;
- не запускаются автоматически несколькими приложениями;
- проектируются совместимыми с предыдущей версией приложения на время отката.

| /api/v1/projects/{id}/source-maps | CI проекта               | секретный project-scoped upload token                 |
| /api/auth/\*                      | участник кабинета        | invitation/password/TOTP и session cookie             |
| /api/v1/dashboard/\*              | личный кабинет           | session cookie + серверная роль + team/project access |

Эти способы доступа нельзя взаимозаменять. Bootstrap-токен работает только до завершения первоначальной настройки. DSN не принимается в dashboard API, CI-токен не читает данные, а пользовательская session cookie не используется npm-пакетом.

## Docker и локальная разработка

### Локальный режим

Docker Compose поднимает PostgreSQL и при необходимости Caddy; приложения можно запускать через Yarn с hot reload. Должна быть и полностью контейнерная команда, близкая к production.

Предусматриваются:

- `.env.example` без секретов, но с пустым `NPM_TOKEN=`;
- корневой `.env` в `.gitignore` для локального `NPM_TOKEN` и локальных секретов;
- генерация локальных безопасных значений;
- автоматическое применение миграций;
- seed с тестовым workspace/project;
- fixture для browser SPA и React SPA для сквозных тестов;
- локальный SMTP catcher принимает тестовые приглашения и письма сброса пароля без отправки во внешний интернет.

### Production

Первая установка — один Linux-сервер:

- Caddy принимает только 80/443 и выдаёт TLS;
- dashboard и ingest имеют разные origins и разные upstream; ingest не обслуживает auth/dashboard routes, а dashboard не принимает Envelope;
- отдельные контейнеры web, ingest, worker-events, worker-mail, worker-retention, migrate и postgres;
- именованные volumes для PostgreSQL, source maps, Caddy и runtime-конфигурации;
- health checks;
- ограничение CPU, памяти и размера логов;
- web, ingest и worker работают не от root, с read-only root filesystem и временным tmpfs;
- Linux capabilities удаляются, privileged mode и mount Docker socket запрещены;
- PostgreSQL не публикует порт на host interface;
- неизменяемые образы с тегами Git SHA и stable;
- миграция выполняется до запуска новой версии;
- секреты не попадают в image layers и публичные env;
- SMTP credentials хранятся только в серверной конфигурации секретов;
- production PostgreSQL volume размещается на зашифрованном диске/volume инфраструктуры;
- перезапуск контейнера не теряет данные.

Web не открывает HTTP port, а worker не сообщает readiness, если отсутствует обязательный production secret, схема содержит неприменённую миграцию или обязательная зависимость недоступна. Проверка выполняется до приёма пользовательского трафика.

Уточнение состава образов от 2026-09-09: приложения и migrate собираются на закреплённом по digest официальном Node 24 Alpine. Эта база исключает неиспользуемые приложениями Perl, GnuTLS и glibc из прежнего Debian-образа; OpenSSL получает обновления безопасности при сборке. Native-зависимости собираются/устанавливаются для musl в том же build stage. Из конечных образов удалены npm, Corepack и Yarn. Отдельный workspace `apps/migrate` содержит Prisma CLI и запускает миграции и первоначальный seed через скомпилированный Node entry point; тестовые PostgreSQL, Vite, Playwright и остальные devDependencies в migrate не входят. Совместимость проверяется Linux Docker установкой, обновлением и откатом.

### Контроль состояния самого GetException

Отказ от продуктовых уведомлений об ошибках не отменяет технический контроль сервиса:

- каждый процесс имеет отдельные liveness и readiness endpoints;
- readiness ingest становится отрицательным, если нельзя безопасно записать inbox;
- readiness web проверяет критическую связь с PostgreSQL;
- Worker сообщает возраст самой старой необработанной записи;
- внутренние метрики считают принятые/отклонённые события, глубину inbox, dead-letter, свободное место и время последнего backup;
- endpoint метрик не публикуется в интернет;
- Docker ограничивает размер и ротацию stdout/stderr логов;
- Caddy access log исключает query string и чувствительные заголовки.

Подключение внешнего мониторинга сервера зависит от инфраструктуры компании и не входит в пользовательские alerts GetException.

## Bootstrap, обновление и откат

Однострочный bootstrap по примеру референсных проектов:

- проверяет Docker/Compose и системные требования;
- создаёт отдельный каталог установки;
- скачивает версионированный bundle;
- генерирует секреты;
- записывает .env с ограниченными правами;
- запускает миграции;
- поднимает сервисы;
- проверяет health endpoint;
- выводит одноразовый URL с bootstrap-токеном для первого открытия кабинета.

Bootstrap устанавливает файлы в `/opt/getexception`. Изменяемые данные находятся в `/opt/getexception/runtime`, а скачанный bundle и Docker images считаются заменяемыми. Bundle содержит только production Compose, шаблоны Caddy и runtime-конфигурации, installer и необходимые metadata. Исходники, тесты, документация, локальные fixtures и development config в bundle не входят.

Installer поддерживает `--install-dir`, `--archive-url`, `--skip-start` и передачу заранее созданных секретов через environment. Он использует `mktemp` и удаляет временный каталог через `trap`. Installer не устанавливает Docker автоматически. Если Docker или Compose отсутствуют, он останавливается и выводит отдельную инструкцию.

Реализация installer использует небольшой shell bootstrap (`mktemp`/`trap`) и Python 3 со стандартной библиотекой. Для проверки attestations требуется GitHub CLI. Команды `install`, `update`, `rollback`, `status` используют один controller. В установке сохраняются неизменяемые каталоги `releases/<SHA>`, атомарный указатель `current` и отдельный `runtime`. Обновление принимает явный release SHA; выбор последнего релиза не может незаметно заменить уже проверенный SHA в deploy job. Параллельные команды блокируются файловым lock. Значения `.env` никогда не исполняются shell.

Перед миграцией обновление делает согласованный локальный backup PostgreSQL. Предыдущие сервисы останавливаются перед миграцией; для первого прототипа допускается короткий перерыв обслуживания. Неудачная миграция блокирует дальнейшее обновление и требует оператора: автоматического отката схемы нет. При неудачном запуске новой версии controller возвращает предыдущий release только если metadata явно разрешают его schema version. После аварийного прерывания незавершённая операция остаётся в журнале, повторный update блокируется до проверки оператором. Backup базы и резервирование конфигурации/ключей — разные операции; локальный backup не заменяет внешнюю резервную копию.

Production deploy в GitHub включается отдельной repository variable после первоначальной установки сервера и настройки защищённого environment. До этого release workflow публикует и проверяет релиз, но не подключается к серверу. CI не создаёт Owner в существующей установке; первичная настройка выполняется только в одноразовом bootstrap E2E stack.

Файл `.env` и runtime-конфигурация создаются только при отсутствии и получают права `0600`. Повторная установка не перезаписывает их. Перед распаковкой installer проверяет checksum и attestation опубликованного bundle. Архив извлекается только после проверки списка путей и запрета absolute path, `..` и symlink за пределы каталога установки.

По этому URL оператор открывает мастер первоначальной настройки, задаёт домен установки и создаёт root-пользователя. Установка считается готовой только после настройки TOTP и успешной проверки dashboard и ingest origins.

Уточнение от 2026-09-10: контактный `ACME_EMAIL` необязателен; HTTPS по-прежнему требует подтверждения владения доменом и доверенного сертификата. Первый запуск с `--defer-ingest-dns` разрешает настроить кабинет до появления DNS ingest: проверяются публичный HTTPS кабинета, закрытые маршруты и внутренняя готовность сервисов. В состоянии установки сохраняется `ingestDnsPending`; полная готовность и автоматический deploy требуют последующей проверки ingest origin и приёма события. Этот флаг нельзя использовать для обновления существующей установки или вместо обязательного ingestion smoke.

На сервер без GitHub credentials можно передать заранее скачанные attestation bundle и trusted root и проверить подпись offline средствами GitHub CLI. Проверки repository, signer workflow, ветки `stable`, точного commit SHA и checksum остаются обязательными; bootstrap, controller и архив проверяются до исполнения или распаковки.

Однострочная команда сначала скачивает небольшой bootstrap и его опубликованный checksum/attestation, проверяет их, и только затем запускает установку. В документации также остаётся ручной вариант «скачать, проверить, запустить» для операторов, которые не разрешают pipe в shell.

Повторный запуск идемпотентен: он не заменяет .env, не удаляет базу, source maps или конфигурацию.

Откат использует предыдущие Docker-образы по SHA. Миграции должны быть backward-compatible как минимум на один deploy: сначала добавление схемы, затем код, удаление старых полей — отдельным поздним релизом.

## CI/CD

### Pull request в stable

- `yarn checks`, который также обязателен перед каждым локальным коммитом;
- неизменяемая установка зависимостей;
- format check;
- ESLint;
- TypeScript;
- проверка разрешённых зависимостей и runtime-границ между workspaces;
- unit tests;
- интеграционные тесты PostgreSQL;
- контракты `@getexception/browser` и `@getexception/react` с ingest;
- тесты ролей и межпроектного доступа;
- тесты очистки чувствительных данных;
- build всех приложений и пакетов;
- проверка Docker Compose;
- проверка миграций на пустой и обновляемой БД;
- dependency, license и secret scanning;
- сборка и smoke test bootstrap bundle.

GitHub Actions запускает `yarn checks` как единый обязательный шаг, включая PostgreSQL integration и Linux Docker bootstrap test из исходников. При локальной проверке на macOS Docker test явно пропускается; в Linux CI отсутствие Docker является ошибкой. Опубликованные registry и bootstrap artifacts проверяются отдельными release jobs. Все jobs имеют `timeout-minutes` и минимальный блок `permissions`. Установка зависимостей всегда выполняется через `yarn install --immutable`.

### Push в stable

Уточнение от 2026-09-09: сервер и SDK выпускаются независимо. Для первого развёртывания публикация SDK откладывается; серверный workflow не использует npm credentials и не повышает версии пакетов. Это позволяет обновлять установку без доступа к npm, сохраняя проверки совместимости SDK в исходниках и тесты установки.

1. `Release` проверяет исходный commit и запускает `yarn checks`;
2. собираются Docker-образы и публикуются в GHCR с stable и Git SHA;
3. критические уязвимости образов блокируют продолжение;
4. публикуется bootstrap artifact с checksums и attestations;
5. fixture из того же checkout отправляют handled и unhandled ошибки в установленный из опубликованного bundle одноразовый stack;
6. проверяются настройка Owner, очистка, группировка, обновление, откат и восстановление backup;
7. проверенный prerelease становится релизом, доступным установщику;
8. при включённом deploy production обновляется строго по SHA, затем запускаются health и ingestion smoke checks.

Два production deploy не могут идти одновременно. Workflow использует `concurrency` с `cancel-in-progress: false`. Основная ветка и release environment защищены review rules.

Серверный workflow разделён на jobs `prepare-release`, `checks`, `build-images`, `publish-bootstrap`, `bootstrap-e2e`, `promote-release` и `deploy`. Каждый job получает только нужные secrets и permissions. `deploy` зависит от успешного завершения серверных publish и smoke jobs. Проверка remote `stable` запрещает выпуск устаревшего commit.

### Отдельный выпуск SDK

Ручной `Prepare SDK release` запускает проверки, повышает общую patch-версию SDK и создаёт release commit. После этого он вызывает отдельный `SDK release` на точном SHA. Серверный workflow не зависит от этих jobs; автоматический commit SDK использует `[skip ci]`.

Подготовка SDK повторно читает remote `stable` перед публикацией. Если ветка уже перешла на посторонний commit, job завершается без публикации старого кода. Если найден ожидаемый автоматический release commit с `[skip ci]`, workflow повторно использует его и не создаёт цикл release commits.

`publish-packages` передаёт GitHub Secret `NPM_TOKEN` как `NODE_AUTH_TOKEN` и `YARN_NPM_AUTH_TOKEN` только на время публикации. Job сначала проверяет, существует ли версия в npm, затем публикует отсутствующую версию с provenance. `registry-smoke` ждёт появления версии, скачивает настоящий tarball и устанавливает его в чистые browser SPA и React SPA fixtures.

SDK workflow проверяет эти опубликованные fixtures в одноразовом Docker stack, включая отправку событий. Публикация SDK не создаёт серверный release и не запускает SSH deploy.

`bootstrap-e2e` скачивает installer и bundle из опубликованного GitHub Release в чистую среду. Тест запускает Compose, открывает `/setup`, вводит bootstrap token, создаёт root-пользователя, настраивает TOTP и домен, затем проверяет вход и приём тестового события.

Дополнительные правила supply chain:

- GitHub Actions получают минимальные permissions для каждого job;
- сторонние Actions закрепляются по полному commit SHA;
- pull request из fork не получает production, `NPM_TOKEN`, SMTP или S3 secrets;
- `NPM_TOKEN` хранится в GitHub Secret, передаётся только защищённому publish job и маскируется в логах;
- локальный `NPM_TOKEN` хранится только в `.env`, а `.env` и созданный на время публикации `.npmrc` запрещены secret scan и `.gitignore`;
- изменения SDK, release workflow и package contents требуют CODEOWNERS и независимого approval;
- наблюдаемые приложения закрепляют проверенную версию SDK и обновляют её через обычный review;
- runtime dependencies SDK минимальны, install scripts запрещены без отдельного обоснования;
- Docker-образы получают SBOM и build attestation;
- deploy использует образ по digest/SHA, а не изменяемый stable tag;
- критические уязвимости runtime image блокируют release либо требуют явно задокументированного временного исключения;
- production environment требует ручного approval уполномоченного участника;
- release commit не запускает бесконечный цикл повторной публикации.

## Лицензирование

Используется разделённая модель:

- серверные приложения web, ingest, worker и их общие внутренние пакеты — Elastic License 2.0;
- уточнение первой итерации от 2026-09-07: `packages/protocol` (wire types, bounded parser и sanitizer), включаемый в публичные SDK, имеет MIT; пакет остаётся внутренним (`private: true`) и встраивается в SDK при сборке. Это исключение позволяет независимо повторять одну проверяемую схему очистки на клиенте и сервере без включения ELv2-кода в MIT SDK;
- публичные пакеты `@getexception/browser`, `@getexception/react` и `@getexception/cli` — MIT;
- переиспользуемые части официального Sentry JavaScript SDK сохраняют исходные MIT notices;
- репозиторий содержит корневое объяснение границ лицензий и отдельные LICENSE-файлы в публикуемых пакетах;
- CI проверяет, что npm package tarball содержит правильную лицензию и third-party notices.

MIT позволяет без ограничений подключать клиентские пакеты к приложениям. ELv2 позволяет использовать, изменять и распространять сервер, но запрещает предоставлять существенную часть его возможностей третьим лицам как конкурирующий hosted/managed service. Перед публичным выпуском формулировки и границы пакетов проходят юридическую проверку.

Сервер под ELv2 следует называть **source-available**, а не open source в строгом смысле OSI. Клиентские пакеты под MIT являются open source.

## Резервное копирование

Принят упрощённый режим, потому что потеря истории ошибок допустима:

- один раз в сутки выполняется сжатый дамп PostgreSQL;
- дамп шифруется до отправки;
- во внешнем S3-совместимом хранилище сохраняются только 3 последние копии;
- source maps отдельно не копируются и при необходимости повторно загружаются из CI;
- отдельные архивы event storage не создаются;
- автоматическая ежемесячная проверка восстановления не входит в MVP;
- перед первым production-запуском процедура восстановления проверяется вручную и документируется.

Таким образом, при аварии допустима потеря событий максимум примерно за 24 часа. Если одновременно потеряны production-сервер и CI-артефакты, старые source maps могут быть невосстановимы. Аккаунты, команды и настройки проектов восстанавливаются из дампа PostgreSQL.

S3 credentials и ключ шифрования хранятся отдельно от backup и production-базы. Дамп не содержит открытых CI-токенов: сервис хранит только их хеши.

Runtime credential backup job может только создать объект под уникальным именем и не может читать, перезаписывать или удалять старые копии; срок хранения применяет отдельная bucket lifecycle policy. Для restore используется отдельный read credential, который не находится постоянно в production-процессах. Bucket закрыт от public access; checksum/signature проверяется до восстановления. Versioning включён. Object Lock включается при наличии поддержки выбранным S3-хранилищем.

| Скомпрометирован npm-пакет                      | Минимум зависимостей, lockfile, review, protected publish, provenance                            | Supply-chain атака может украсть данные до серверной фильтрации         |
| Украдена БД или backup                          | Минимизация, шифрование backup, ограниченный retention                                           | Сохранённые диагностические данные всё равно чувствительны              |
| Ошибка GetException раскрывает payload в логах  | Запрет raw-body logging, структурные безопасные логи, тестовые canary secrets                    | Нужно постоянно проверять новые места логирования                       |
| Зависимость пытается отправить события наружу   | Нет analytics/CDN, egress allow-list, ingest/worker без интернета                                | Компрометация host или web с разрешённым egress остаётся критической    |
| Подделан X-Forwarded-For                        | Caddy заменяет клиентский заголовок доверенным адресом                                           | Распределённый ботнет всё равно имеет много реальных IP                 |
| Захвачен production host/Docker daemon          | Ограниченный SSH, firewall, обновления, encrypted volume, отсутствие Docker socket в контейнерах | Root host контролирует всю установку                                    |

## Отклонённые варианты

### Постоянный HMAC/JWT-секрет внутри browser SPA

Отклонён: секрет попадёт к каждому пользователю вместе с JavaScript. Схема создаёт ложное чувство проверки источника.

### Полностью собственный browser SDK

Отклонён: корректно перехватывать ошибки разных браузеров и разбирать stack trace сложно. Повторное использование официальных MIT-компонентов Sentry снижает риск и упрощает миграцию.

### Принимать публичные ошибки внутри процесса Next.js

Отклонён: анонимный трафик получил бы общие ресурсы и более широкие права с личным кабинетом. Разделение на контейнеры имеет низкую инфраструктурную стоимость и уменьшает последствия атаки.

### Добавить Redis сразу

Отклонён для начального объёма. PostgreSQL обеспечивает надёжную ограниченную очередь. Граница Worker позволяет заменить её позже по измерениям.

### Хранить source maps прямо в PostgreSQL

Отклонён: это крупные файловые артефакты с другим жизненным циклом. В PostgreSQL остаются метаданные, файлы — в закрытом object-storage интерфейсе.

### Разрешить произвольные поля Sentry, а потом удалять опасные

Отклонён: новые или забытые поля могут незаметно сохранить данные. Безопаснее собирать новый объект только из короткого утверждённого списка.

## Последствия решения

Положительные:

- переход с Sentry требует главным образом заменить import и DSN;
- единый сервис обслуживает несколько browser SPA и React SPA;
- утечка публичного DSN не раскрывает уже сохранённые ошибки;
- строгая минимизация уменьшает объём чувствительных данных;
- отдельные процессы дают понятные права и возможность масштабирования;
- PostgreSQL-only MVP проще поддерживать;
- CI-токен никогда не попадает конечному пользователю.

Компромиссы:

- нельзя полностью запретить фальшивые события из публичного SPA;
- контекста будет меньше, чем в Sentry с настройками по умолчанию;
- совместимость поддерживается только для явно описанной части SDK;
- source maps и свой CLI добавляют отдельный pipeline;
- несколько runtime-процессов и ролей БД сложнее одного Next.js-контейнера;
- безопасность зависит не только от кода, но и от корректного деплоя, backup и управления секретами.

## Сводка принятых решений

1. Название продукта и monorepo — GetException.
2. Этот ADR является отправной точкой для реализации MVP.
3. Одна установка обслуживает одну компанию и одно рабочее пространство на отдельном Linux-сервере.
4. Публикуются отдельные SDK `@getexception/browser` и `@getexception/react`, совместимые с выбранной частью API соответствующих Sentry-пакетов.
5. Пакет `@getexception/cli` загружает source maps и не копирует весь sentry-cli.
6. Используется публичный write-only DSN, а не секрет или JWT в браузере.
7. Данные принимаются по строгому allow-list, а чувствительные поля отбрасываются.
8. Регистрация доступна только по одноразовому приглашению, привязанному к подтверждённому email. Вход выполняется по email и паролю без Google OAuth.
9. При первом открытии оператор задаёт домен установки и создаёт root-пользователя через защищённый bootstrap flow.
10. TOTP обязателен для Owner, настраивается через зашифрованный pending credential и защищён от повторного использования кода.
11. Роли Owner, Developer и Viewer действуют во всём рабочем пространстве, а команды ограничивают набор проектов.
12. Developer и Viewer видят только проекты назначенных команд, а Owner видит все проекты.
13. Сохраняются только ошибки уровней error и fatal.
14. Сохраняется только безопасная техническая история перед ошибкой.
15. Разрешены стандартные tags и настраиваемый Owner allow-list.
16. Выбраны базовые правила группировки и повторного открытия регрессии.
17. Релиз основан на полном Git SHA, а source maps связываются через Debug ID.
18. Уведомления не входят в MVP.
19. Начальная ёмкость составляет 100 000 событий в сутки и всплеск 50 событий в секунду.
20. Из Selfchecks, Selflify и AppNotes взяты конкретные схемы monorepo, TOTP, background workers, bootstrap, миграций и release checks.
21. Кабинет использует `@base-ui/react`, Tailwind и семантические CSS-переменные.
22. Утверждена browser support policy без Internet Explorer.
23. Приглашения и password reset записываются в transactional outbox и доставляются отдельным worker через SMTP.
24. Утверждены начальные rate limits, суточные квоты и явный отказ без sampling.
25. Проект можно восстановить 7 дней, затем он окончательно удаляется.
26. Сервер лицензируется под ELv2, а публичные SDK и CLI под MIT.
27. Backup включает ежедневный зашифрованный PostgreSQL dump и 3 внешние копии. Source maps не копируются.
28. Dashboard и ingest работают на разных origins, а host-only cookie кабинета никогда не отправляется на ingest.
29. У процессов и backup отдельные ограниченные PostgreSQL-роли, а unsafe raw SQL запрещён.
30. Все поля события остаются недоверенными после хранения и выводятся только как текст.
31. Сброс TOTP Owner нельзя выполнить только через email. Нужен recovery-код, другой Owner или offline bootstrap recovery.
32. Публикация npm-пакетов использует секрет `NPM_TOKEN` из локального `.env` или GitHub Secrets.
33. Publish job ограничивает доступ к `NPM_TOKEN`, а CI проверяет provenance и состав опубликованных tarball.
34. Лендинг хранится в отдельном репозитории `getexception.github.io` и публикуется независимо через GitHub Pages.
35. Подробный security audit и его блокирующие production-требования являются частью решения.

## Критерии приёмки MVP

### Подключение и совместимость

- fixture browser SPA и React SPA подключаются заменой импорта Sentry и DSN без переписывания поддерживаемых вызовов;
- captureException, captureMessage уровня error/fatal, ErrorBoundary, unhandled error и unhandled rejection доходят до проекта;
- поддерживаемый Envelope от закреплённой версии официального Sentry SDK проходит контрактные тесты;
- неподдерживаемые transaction, replay, attachment и другие типы не сохраняются и дают документированное поведение;
- оба опубликованных SDK проверяются после установки из настоящего registry, а не только из workspace;
- publish job получает `NPM_TOKEN` только из GitHub Secret, а pull request и runtime-контейнеры не имеют доступа к нему.

### Диагностика

- одинаковые события объединяются в одну группу;
- различающиеся причины не объединяются только из-за похожего текста;
- новое событие решённой группы открывает regression;
- release отображается и фильтруется;
- после загрузки корректной source map stack trace показывает исходный файл, функцию, строку и колонку;
- поздно загруженная карта запускает повторную обработку unresolved stack frames;
- безопасные breadcrumbs показывают маршрут и технический API-шаг без запрещённых данных.

### Безопасность и приватность

- canary secrets из URL, cookie, storage, формы, state, API body и error object отсутствуют в сети, логах, БД и кабинете;
- transport использует `credentials: omit`/`no-referrer`, не добавляет Authorization, не использует `sendBeacon`, а session cookie кабинета отсутствует в запросе ingest;
- DSN не позволяет прочитать событие, загрузить source map или вызвать dashboard API;
- CI-токен не позволяет читать события или менять проект;
- запрос с неподходящим browser Origin отклоняется;
- отдельно документированный тест показывает, что поддельный non-browser Origin остаётся возможным и ограничивается квотой, а не ошибочно считается аутентификацией;
- Viewer не может разрешить ошибку даже прямым API-запросом;
- Developer и Viewer не могут получить проект чужой команды заменой ID;
- те же проверки работают для фильтров, cursor, server actions и любого debug/export endpoint;
- свободная signup-попытка без приглашения не создаёт Account или Member;
- истёкшее, отозванное или повторно использованное приглашение не принимается;
- приглашение нельзя принять аккаунтом с другим или неподтверждённым email;
- утечка invitation URL без доступа к почте приглашённого не позволяет установить пароль или создать Account;
- повторная отправка меняет токен и срок, а предыдущее письмо перестаёт давать доступ;
- два параллельных запроса принятия создают не более одного Member и один набор team membership;
- роль и команды берутся из заблокированной записи приглашения, а не из тела регистрации или принятия;
- anonymous preview маскирует email, не раскрывает наличие аккаунта и не возвращает токен;
- GetException не создаёт многоразовые invitation links без привязки к email;
- прямой вызов стандартного Better Auth invitation route не позволяет создать или принять приглашение в обход GetException;
- Owner после password-входа не получает рабочую сессию без TOTP или recovery-кода;
- password reset не отключает TOTP; Owner MFA recovery следует отдельной утверждённой процедуре и отзывает сессии;
- сохранённый текст ошибки не исполняется как HTML/JavaScript;
- SQL payload во всех строковых полях остаётся текстом; unsafe Prisma API отсутствует, а ingest получает `permission denied` при чтении auth/session/error tables;
- `__proto__`, `prototype`, `constructor`, глубокий JSON, compression bomb и control characters не меняют объект приложения, не вызывают OOM и не подделывают логи;
- server-assigned `received_at` управляет квотой/retention, а невозможные client timestamp и чрезмерная кардинальность release/environment/fingerprint ограничиваются;
- Host-header/open-redirect не может изменить домен invitation/reset URL или назначить пользователю роль;
- попытки path traversal и zip bomb при source-map upload отклоняются;
- source-map parser ограничен по времени/памяти, не имеет internet egress и не останавливает очередь на одном плохом файле;

### Надёжность и нагрузка

- при нормальной нагрузке ingest отвечает после durable inbox insert, не ожидая symbolication;
- при всплеске 50 событий/секунду система остаётся доступной и не теряет уже принятые события;
- превышение лимита возвращает 429 и увеличивает видимый счётчик отказов;
- перезапуск Worker продолжает необработанные задачи без создания дублей;
- повтор события с тем же project ID + event ID не создаёт вторую запись;
- poisoned event переходит в dead-letter и не останавливает очередь;
- сбой или timeout GetException не ломает и заметно не задерживает работу наблюдаемого SPA.

### Установка и восстановление

- опубликованный bootstrap bundle разворачивает чистый сервер одной командой;
- первое открытие требует bootstrap-токен и позволяет один раз настроить домен, root-пользователя и его TOTP;
- после завершения настройки `/setup` нельзя использовать повторно, а вход через Google отсутствует;
- повторный bootstrap не заменяет секреты и не удаляет volumes;
- миграции проходят и на пустой, и на предыдущей версии БД;
- откат образов на предыдущий SHA работает с новой схемой;
- ручное восстановление одного из зашифрованных pg_dump возвращает аккаунты, команды и настройки проектов;
- runtime backup credential не может читать/удалять копии, а отдельный restore credential и checksum позволяют проверить восстановление;
- удаление проекта немедленно отключает его ключи, допускает восстановление 7 дней и затем удаляет данные;
- source maps и PostgreSQL переживают обычный restart/upgrade контейнеров.

### Производительность кабинета

- при расчётном объёме типовой список групп с фильтром открывается на сервере не дольше 1,5 секунды в p95;
- ingest при нормальной нагрузке подтверждает durable приём не дольше 200 мс в p95 внутри production-сети;
- тяжёлая группировка, очистка retention и symbolication никогда не выполняются синхронно в web или ingest request.
